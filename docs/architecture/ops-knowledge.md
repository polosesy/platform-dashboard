# 사례·런북 — 경험으로 빨리 정상화하기

2026-11-13 검토·1단계 구현입니다. 장애나 오류를 겪고 고친 경험을 팀이 **사례**로 남깁니다. 반복되는 대응 절차는 **런북**으로 정리합니다. 새 오류가 오면 비슷한 사례와 그때 쓴 런북을 바로 찾습니다. 화면은 알림·대응 › 사례·런북(`/runbooks`)입니다.

## 1. 왜 필요한가 (오늘의 빈칸)

| 지금 있는 것 | 빈칸 |
|---|---|
| 알림 센터: 무슨 일이 일어났나(Azure·Grafana 알림 수신·확인) | 이 알림을 **전에 어떻게 고쳤는지**가 어디에도 없다. 확인 메모는 알림과 함께 30일 뒤 지워진다 |
| 통합 위험 이슈 목록: 보안 위험의 상태·담당·예외 | 보안 위험만 다룬다. 앱·인프라 오류는 다루지 않는다 |
| `docs/troubleshooting/error-catalog.md`: 플랫폼 개발팀의 오류 사전 | 저장소 문서라 운영자가 쓰거나 고칠 수 없다. 고객 환경의 경험도 아니다 |
| 각 화면의 사실(히트맵·이벤트·로그·Hubble) | 같은 신호(`OOMKilled`, `UNSUPPORTED_L3_PROTOCOL`, `AADSTS700016` …)가 다시 와도 매번 처음부터 조사한다 |

예: 2026-11-13 stg에서는 hubble-ui backend가 OOMKilled되었고, 원인(채널 누수)과 조치(채널 줄이기·한도 512Mi)를 찾는 데 몇 시간이 걸렸습니다. 같은 증상이 다시 오면 `OOMKilled · hubble-ui`로 이 경험을 1초 안에 찾아야 합니다.

## 2. 전문가 토론

| 분야 | 주장 | 반론·보완 | 결론 |
|---|---|---|---|
| SRE | 장애 회고(postmortem)의 핵심은 증상·영향·원인·조치·교훈이다. 이 다섯 칸을 강제하면 쓰는 사람이 지친다 | 지식 관리: 빈 칸이 많으면 찾아도 쓸모가 없다 | **증상만 필수**. 나머지는 선택이고, '해결됨'으로 바꿀 때 조치를 요구한다 |
| 지식 관리 | 사례(무슨 일이 있었나)와 런북(무엇을 하라)은 다르다. 섞으면 둘 다 낡는다 | SRE: 런북만 있으면 '언제 썼고 통했나'가 없다 | **둘을 나누고 잇는다**. 사례가 쓴 런북을 가리키고, 런북의 '쓰인 횟수·마지막 사용'은 사례에서 **계산**한다(저장하지 않음 — 꾸밀 수 없음) |
| 검색 | 비슷함은 글자보다 **신호**가 정확하다(같은 `OOMKilled`, 같은 알림 규칙, 같은 드롭 사유) | 글로만 쓴 사례도 많다 | 신호(정확히 같음) + 글 유사도(TF-IDF 코사인, 한글은 두 글자씩) + 범위(같은 워크로드·네임스페이스)를 합친다. **왜 비슷한지**(겹친 신호·단어·범위)를 항상 보인다 |
| 에이전트(AI) | LLM이 증상을 읽고 원인·조치를 제안하면 가장 빠르다 | 보안: 고객의 로그·이름이 외부 모델로 나간다. '사실만 보인다' 원칙과 충돌하고, 승인된 키·전송 범위가 없다 | **1단계는 '경험 도우미'**: 규칙·유사도만 쓰고 외부 전송 없이 '이 사례들에서 쓴 런북의 첫 단계'를 묶어 보인다. LLM 초안 작성(2단계)은 8절의 결정 뒤에 한다 |
| 보안 | 붙여 넣은 오류에 토큰·연결 문자열이 섞인다 | — | 저장할 때 로그 가리기(`logRedaction` — JWT·Bearer·key=값·SAS·PEM)를 적용하고 가린 수를 기록한다 |
| 보안 | 고객 B 클러스터의 사례를 고객 A 운영자가 보면 안 된다 | — | 사례에 클러스터를 고르면 그 **연결**을 저장하고, 읽을 때 내 역할이 쓸 수 있는 연결의 사례만 보인다 |
| 보안 | 누가 써도 되나 | — | 읽기와 찾기는 로그인, 쓰기는 운영자 이상이다(이슈 상태·팀 질문과 같음). 개정 번호(rev)가 다르면 409를 낸다 |
| UX | 장애 중에 새 화면을 찾아가지 않는다 | — | **입구를 장애가 보이는 곳에 둔다**: 알림 상세의 '비슷한 경험 찾기'(규칙·제목·대상이 채워짐), 찾기 결과의 '이 내용으로 사례 기록' |
| UX | 점수 %는 거짓 정밀함이다 | — | 강함·보통·약함 세 단계와 이유 칩으로 보인다 |
| 데이터 | 효과를 재야 계속 쓴다 | — | 1단계: 런북별 '해결한 사례 n·마지막 사용'. 2단계: 알림 → 사례 연결로 재발률과 해결 시간 |

## 3. 데이터 (`packages/types/src/runbook.ts`)

- **사례 `OpsCase`**
  - 제목·상태(열림 → 완화 → 해결)·심각도(sev1–4)·발생·해결 시각
  - **증상**(필수)·원인·조치·교훈·태그
  - **신호** `OpsSignal{kind, value}`. 종류는 K8s 이유·종료 코드·드롭 사유·알림 규칙·HTTP 상태·오류 코드·예외·리소스 유형·키워드다.
  - 범위: 클러스터·네임스페이스·워크로드·리소스 유형
  - 쓴 런북 ID, 출처(알림 ID 또는 직접), 작성·수정자(표시 이름)·rev
- **런북 `OpsRunbook`**
  - 제목·**언제 쓰나**·신호·태그
  - **단계**(제목·설명·명령(복사만, 실행 안 함)·확인 방법)·되돌리기·팀·마지막 검증일
- **저장**: `<AUD_ARRANGEMENT_DIR>/knowledge/knowledge.json`(없으면 메모리 + 화면 경고). 쓰기는 임시 파일 → rename, 한 번에 하나씩이다. 상한은 사례 2,000개·런북 300개, 글자 수는 칸마다 정해져 있다.

## 4. 비슷함 계산 (`services/opsMatch.ts`, 순수)

1. **신호 뽑기** `extractSignals(text)`
   - 알려진 Kubernetes 이유(OOMKilled·CrashLoopBackOff·ImagePullBackOff·FailedScheduling·Evicted …)
   - `exit code 137`
   - Cilium 드롭 사유(UPPER_SNAKE)
   - Azure·Entra 오류(`AADSTS\d+`, `…Failed/NotFound/Exceeded/Denied`)
   - Java·.NET 예외(`…Exception/Error`)
   - `HTTP 5xx`
   - 이 플랫폼의 오류 코드(`hubble_ui_unsupported` 같은 snake_case)
   - 붙여 넣은 글에서도, 저장된 사례에서도 같은 함수를 쓴다.
2. **글 유사도**
   - 영문은 낱말, 한글은 두 글자씩 자른다(조사를 떼어 낼 필요가 없음).
   - 사례·런북 모음 전체로 IDF를 매긴 TF-IDF 코사인이다.
3. **범위**: 같은 워크로드 1 · 네임스페이스 0.5 · 리소스 유형 0.4 · 클러스터 0.3(최대 1)
4. **점수** = 0.5 × 글 + 0.35 × (겹친 신호 / 찾는 신호) + 0.15 × 범위 (+ 조치가 적힌 해결 사례 0.05)
   - 신호도 범위도 안 겹치고 글 유사도가 0.15 미만이면 빼서 노이즈를 줄인다.
   - 사례·런북 각각 상위 5개를 보인다.
   - 강함 ≥ 0.45 · 보통 ≥ 0.25 · 그 밖 약함
5. **경험 도우미**
   - 비슷한 사례가 가리킨 런북과 신호로 직접 맞은 런북을 합친다. '사례 n건에서 쓰임'을 함께 보인다.
   - 가장 위 런북의 단계를 '먼저 해 볼 것'으로 보인다.
   - 판단은 운영자가 한다. 명령은 복사만 하고 실행하지 않는다.

## 5. API (`routes/ops.ts`)

| 경로 | 권한 | 내용 |
|---|---|---|
| `GET /api/ops/knowledge` | 로그인 | 내가 볼 수 있는 사례·런북 + 런북별 사용(사례에서 계산) + `durable`·`canWrite` |
| `PUT /api/ops/cases?id=` · `DELETE …&baseRev=` | 운영자 | 사례 만들기(id 없음)·고치기·지우기. rev가 다르면 409, 내 역할이 못 쓰는 클러스터면 403 |
| `PUT /api/ops/runbooks?id=` · `DELETE` | 운영자 | 런북 |
| `POST /api/ops/similar` | 로그인 | `{text, signals?, scope?, exclude?}` → 뽑은 신호 · 비슷한 사례·런북(이유 포함) · 경험 도우미 |

익명이면 빈 목록이고, 예시 데이터는 없습니다(사실만 보인다).

## 6. 화면 (`/runbooks`)

- **찾기**(기본): 오류·증상 붙여넣기(URL `?q=`로 채울 수 있음) → 뽑은 신호 칩 → **경험 도우미**(추천 런북과 첫 단계) → 비슷한 사례(이유 칩·그때의 조치) → 비슷한 런북 → '이 내용으로 사례 기록'
- **사례**: 찾기·상태 필터·목록 → 상세(증상·원인·조치·교훈·신호·쓴 런북) → 고치기(운영자)
- **런북**: 목록(쓰인 사례 n·마지막 사용) → 단계(명령은 복사 블록) → 고치기
- **입구**: 알림 센터 › 알림 상세 › '비슷한 경험 찾기'(규칙·제목·요약·대상)

## 7. 운영 방법

1. 장애 중: 알림 상세 → '비슷한 경험 찾기' → 도우미의 런북부터 본다.
2. 장애 뒤(24시간 안): '이 내용으로 사례 기록' → 원인·조치·교훈 → '해결'로 바꾼다. 같은 조치가 두 번째라면 그 조치를 런북으로 만들고 사례에서 가리킨다.
3. 매월: 런북 목록에서 '마지막 사용'이 오래된 것과 검증일이 없는 것을 정리한다.

## 8. 2단계 — 에이전트 (결정 필요, 미구현)

| 결정 | 선택지 | 권장 |
|---|---|---|
| 모델이 어디서 도나 | Microsoft Foundry의 Claude(고객 Azure 테넌트 안 결제·데이터 경계) / Anthropic API 직접 / 쓰지 않음 | Foundry(고객 거버넌스 안) |
| 무엇을 보내나 | 붙여 넣은 글 + 비슷한 사례의 증상·조치(가린 뒤) / 실시간 신호(이벤트·로그)까지 | 처음엔 글 + 사례만 |
| 무엇을 하게 하나 | 사례 초안(증상·원인 후보·조치 요약) · 런북 단계 초안 · 원인 후보 순위 | 초안만. 저장은 사람이 누름. 명령 실행 없음 |
| 표시 | '에이전트 초안 — 검토 필요' 칩, 근거(어느 사례·어느 신호)를 꼭 붙임 | — |

이음새: `POST /api/ops/similar`의 응답(신호·사례·런북)이 그대로 에이전트의 입력 맥락이 됩니다. 모델이 바뀌어도 검색은 바뀌지 않습니다.
