# Kubernetes 메뉴 구조 검토 — AKS 클러스터 · AKS 모니터링

> 결론(권장): **합치지 않고 역할을 나눈 뒤, 같은 대상(워크로드)으로 잇는다.**
> 'AKS 클러스터' = **구성·리소스**(무엇이 있고 어떻게 설정됐나), 'AKS 모니터링' = **상태·신호**(건강한가).
> 겹치는 숫자는 한 곳에만 두고, 두 화면을 같은 워크로드로 잇는다. 2026-11-11 구현 — 무엇을 했고 무엇이 남았는지는 맨 아래 6절.

## 1. 지금 두 화면 (2026-11-11 코드 기준)

| | AKS 클러스터 (`/kubernetes`) | AKS 모니터링 (`/observability`) |
|---|---|---|
| 출처 | Kubernetes API 목록(연결의 읽기 권한) | Azure Monitor 작업 영역(Prometheus) + Kubernetes API(이벤트·VPA) + Loki |
| 위쪽 숫자 | 노드 · Running 파드 · Deployment · Service | 클러스터 한눈에 보기(워크로드 · Ready 파드 · 레플리카 부족 · 재시작 · OOM) |
| 본문 | 객체 표 하나(14종 — 이름·네임스페이스·종류·상태·Ready·재시작·나이), 종류·네임스페이스 거르기 | 6개 탭: 클러스터 · 워크로드(히트맵·표·K8s 이벤트) · SLO · 노드 · 로그 · 네트워크(Hubble) · 수집 상태 |
| 행을 누르면 | 아무 일 없음(상세·이벤트·로그 없음) | 워크로드 패널(신호 풀이 · 파드 · Warning 이벤트 · VPA · 로그) |

**겹치는 곳**

1. 노드 수 · 파드 상태 · 재시작: 클러스터 카드·객체 표와 모니터링의 한눈에 보기·히트맵 표가 같은 질문에 답합니다. **출처가 달라 숫자가 다를 수 있습니다.** 'Running 파드'는 Kubernetes API의 phase이고, 'Ready 파드'는 kube-state-metrics 기준입니다. Running인데 Ready가 아닌 파드는 두 화면이 다르게 셉니다.
2. Pod 트래픽(`/hubble`)과 모니터링 › 네트워크 탭은 같은 컴포넌트입니다(의도된 중복 — 네트워크 메뉴에서 VNet 흐름과 나란히 보기 위해).
3. 인벤토리: AKS 보안 점검 › 인벤토리(KBOM)도 이미지·워크로드 목록을 가집니다(보안 관점 — 별개 유지).

**클러스터 화면에만 있는 것:** Service · Ingress · ConfigMap · Secret · PVC · Job · CronJob 같은 **워크로드가 아닌 객체**의 목록. 모니터링에는 없습니다.

## 2. 다른 플랫폼은 어떻게 나누나 (공개 콘솔·문서의 일반 구조)

| 플랫폼 | 구조 |
|---|---|
| Azure Portal (AKS) | 클러스터 리소스 하나의 메뉴 안에 'Kubernetes 리소스'(네임스페이스·워크로드·서비스와 인그레스·스토리지·구성·이벤트)와 '모니터링'(Insights·메트릭·로그·경고) 그룹이 나란히 |
| GKE 콘솔 | Kubernetes Engine 메뉴에 클러스터·워크로드·서비스/인그레스·구성(Secret·ConfigMap)·스토리지·객체 브라우저. 관측 값은 클러스터·워크로드 **상세 안의 탭** |
| EKS 콘솔 | 클러스터 상세의 탭: 개요·리소스(객체 브라우저)·컴퓨팅·네트워킹·추가 기능·관측 가능성 |
| Datadog | Infrastructure › Kubernetes 한 곳: 개요 · 탐색기(클러스터·노드·파드·워크로드 …, 행을 누르면 옆 패널에 메트릭·로그·이벤트·구성) · 자동 확장 · 리소스 사용률. SLO·모니터·로그 검색은 플랫폼 공통 메뉴 |
| Grafana Cloud Kubernetes Monitoring | 앱 하나: 클러스터 › 네임스페이스 › 워크로드 › 파드로 내려가며 각 단계에 메트릭·로그·이벤트, 그 밖에 경고·비용·효율 |
| Lens · Headlamp · Rancher | 객체 탐색기가 중심(노드·워크로드·구성·네트워크·스토리지·이벤트), 메트릭은 객체 상세에 |

**공통 패턴**

- (a) Kubernetes는 한 영역입니다.
- (b) **대상 중심**으로 내려갑니다(클러스터 → 네임스페이스 → 워크로드 → 파드).
- (c) 신호(메트릭·로그·이벤트)는 대상을 보는 **렌즈**입니다. 같은 상세 패널에 함께 붙습니다.
- (d) SLO·경고·로그 검색처럼 여러 대상을 가로지르는 기능은 공통 메뉴에 둡니다.

**'구성·리소스'와 '모니터링'을 나눈 곳은 Azure Portal·GKE·EKS(클라우드 콘솔)이고, 하나로 합친 곳은 Datadog·Grafana(관측 플랫폼)입니다.** 이 대시보드는 둘 다 합니다. Azure 구성(ARM)을 읽고, 관측 신호도 읽습니다.

## 3. 선택지

| | 내용 | 좋은 점 | 나쁜 점 |
|---|---|---|---|
| A. 완전 통합 | 메뉴 'AKS' 하나에 탭 8개 이상(구성·리소스·워크로드·SLO·노드·로그·네트워크·수집 상태) | 메뉴가 하나 | 탭이 너무 많음. 출처·권한이 다른 두 세계(Kubernetes API 목록 권한 vs 작업 영역 읽기)가 한 화면에 섞여 한쪽 실패가 화면 전체를 흐림. URL·문서·습관이 바뀜 |
| B. 지금대로 + 클러스터 화면만 보강 | 두 메뉴 유지, 객체 표에 기능 추가 | 변경이 작음 | 숫자 중복·불일치와 "어디서 보지?"가 그대로 |
| **C. 역할 분리 + 대상으로 잇기 (권장)** | 클러스터 = 구성·리소스, 모니터링 = 상태·신호, 같은 워크로드 상세 패널을 공유하고 서로 링크 | 화면마다 질문이 하나. 클라우드 콘솔(구성)과 관측 플랫폼(신호)의 장점을 함께 | 상세 패널 공유 작업이 필요 |

## 4. 권장안 C — 단계

**1단계 — 중복 제거 + 클러스터 화면만의 가치**

- 맨 위 **'클러스터 구성'**(ARM — API가 이미 읽는 값 재사용: `aksReadiness` · `nodeMaintenance` · `workloadIdentity`의 클러스터 문맥)
  - 버전: 지금 버전 · 올릴 수 있는 버전 · 자동 업그레이드 채널 · 노드 OS 채널 · 유지 보수 창
  - 노드 풀: VM 크기 · 수 · 자동 확장 최소/최대 · OS · 모드 · 가용 영역
  - 네트워크: 플러그인 · 데이터 평면(Cilium) · 정책 · Pod/Service 대역 · API 서버(프라이빗·허용 IP)
  - ID: Entra · Azure RBAC · 로컬 계정 · OIDC · 워크로드 ID
  - 추가 기능: 모니터링 · Defender · Azure Policy · ACNS …
- 'Running 파드' 카드를 빼고 **'상태는 AKS 모니터링 →'** 링크로 바꿉니다(파드 숫자는 모니터링 한 곳 — 출처 하나).
- 객체 표에 찾기와 종류 묶음 칩(워크로드 · 네트워크 · 구성 · 스토리지 · 배치 작업)을 넣습니다.

**2단계 — 같은 상세 패널**

- 클러스터 표에서 워크로드 행을 누르면 모니터링의 워크로드 패널(신호 풀이·파드·이벤트·VPA·로그)을 그대로 엽니다.
- Service · Ingress는 셀렉터가 고른 워크로드 · 포트 · 엔드포인트 수를 보여 줍니다. ConfigMap · Secret은 그것을 쓰는 워크로드를 보여 줍니다(**값은 읽지 않음**).
- 모니터링 패널에는 '구성 보기 →'(클러스터 화면의 그 객체) 링크를 둡니다.

**3단계 — 메뉴**

- 메뉴 설명(`nav.desc`)을 'AKS 클러스터 — 구성·리소스' / 'AKS 모니터링 — 상태·신호'로 바꿉니다.
- Pod 트래픽은 네트워크 그룹에 그대로 둡니다(VNet 흐름과 나란히 비교하는 자리).

**하지 않는 것:** YAML 편집 · `kubectl exec` · 재시작 같은 쓰기(읽기 전용 원칙), Secret 값 읽기.

## 5. 전문가 토론 요약

| 관점 | 주장 | 반영 |
|---|---|---|
| SRE | "장애 때는 한 곳에서 상태 → 원인 → 구성까지 이어져야 한다" | 같은 워크로드 패널 공유 + 서로 링크(2단계) |
| 정보 구조 | "탭 8개 이상은 길을 잃는다. 메뉴는 질문 하나에 화면 하나" | 통합(A) 대신 역할 분리(C) |
| 데이터 | "출처가 다른 같은 숫자는 신뢰를 깎는다(Running vs Ready)" | 파드 숫자는 모니터링 한 곳(1단계) |
| 플랫폼 | "Azure 구성 정보는 관측 플랫폼이 못 주는 이 대시보드의 강점" | 클러스터 화면 = 구성 중심(1단계) |
| 보안 | "Secret은 이름·사용처까지만, 값은 절대 안 읽는다" | 2단계 범위에 명시 |

## 6. 구현 (2026-11-11)

| 단계 | 한 것 | 남은 것 |
|---|---|---|
| 1 | **클러스터 구성** 칸(`GET /api/kubernetes/cluster-config` → `services/aksClusterConfig.ts`, ARM만 — 프라이빗이라 클러스터에 못 닿아도 답함): 버전 · 올릴 수 있는 버전(패치/새 마이너/최신 칩) · 채널 · 요금제 · 유지 보수 창, 노드 풀 표(크기 · 수 · 자동 확장 · OS · 영역 · 버전, 컨트롤 플레인과 다르면 '다름'), 네트워크, 로그인 · 추가 기능(● 켜짐 · ○ 꺼짐 · ? 응답에 없음). Azure가 안 준 값은 '—'(추측 금지), 못 읽은 부분은 알림 한 줄. 'Running 파드' 카드 삭제 → 재고 카드(노드 · 워크로드 · 서비스·인그레스 · 배치) + '상태는 AKS 모니터링에서' 링크. 객체 표에 묶음 칩 · 찾기 · 처음 200행 | — |
| 2 | 워크로드 행의 '신호 →' = AKS 모니터링에서 그 워크로드 패널 열기(`?wl=<ns>/<이름>`), 모니터링 패널의 '구성 보기 →' = 이 화면에서 그 워크로드 객체(`?ns=&q=`). Service 행에 포트와 '파드 n개 선택 → 워크로드'(선택기가 지금 고르는 파드, 파드 목록을 읽었을 때만) | 패널을 이 화면 안에서 그대로 열기(지금은 화면 이동), ConfigMap · Secret의 '쓰는 워크로드'(목록 권한이 고객 RBAC 템플릿에 없어 보류 — 값은 어떤 경우에도 읽지 않음) |
| 3 | 메뉴 설명: AKS 클러스터 '구성 · 리소스 — …' / AKS 모니터링 '상태 · 신호 — …' | — |
