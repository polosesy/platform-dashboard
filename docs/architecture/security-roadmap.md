# 보안 기능 고도화 계획 — CNAPP(Wiz) 데모와 비교

이 문서는 클라우드 보안 플랫폼(CNAPP) 데모의 핵심 개념과 이 대시보드의 보안 기능을 나란히 놓고, **빈 곳을 메우는 순서**를 정합니다. 단계마다 설계·완료 조건·상태를 적고, 구현하면 같은 커밋에서 이 문서를 고칩니다.

> **5살 비유**: 도둑이 집에 들어오려면 ① 열린 창문(노출·취약한 이미지) ② 열쇠(권한) ③ 보물(데이터·클러스터)이 이어져야 해요. 따로따로 보면 "창문 하나 열림", "열쇠 하나 있음"이지만, **이어서 보면** "이 창문으로 들어와 이 열쇠로 보물상자를 열 수 있다"가 보여요. 우리는 이미 ②③을 잇고 있었고, ①(어느 창문이 정말 깨질 수 있는지)이 비어 있었어요.

## 1. 비교 기준

참고: "Wiz in Action: Risk-Based Code-to-Cloud Security Monitoring" 데모 영상(본문은 직접 확인 못 함) — 같은 데모를 소개한 [Bridewell 웨비나](https://www.bridewell.com/webinars/detail/seeing-the-full-attack-path-continuous-code-to-cloud-security-with-wiz)와 [Wiz 제품 페이지](https://www.wiz.io/product)의 공개 설명을 기준으로 삼았습니다.

| 개념 | 공개 설명 요지 |
|---|---|
| Security Graph | 코드·클라우드 리소스·ID·취약점·잘못된 구성의 관계를 하나의 그래프로 |
| Issues (toxic combinations) | 따로는 작은 문제들이 겹쳐 실제로 악용될 조합을 **하나의 우선순위 목록**으로 |
| Attack path | 조합을 악용 가능성·영향으로 순위 매겨 다음 조치를 안내 |
| Code-to-Cloud | 실행 중인 리소스를 코드·파이프라인·개발자까지 거슬러 올라감, 수정 PR |
| Projects / 소유 | 조직 구조에 따라 환경을 묶고 접근 권한도 그 단위로 |
| Workflows | 탐지 → 담당자 → 조치를 자동화 |
| Runtime (Sensor) | 실시간 위협 탐지를 위험 맥락과 함께 |

## 2. 지금 상태와 빈 곳

| 개념 | 이 대시보드 | 빈 곳 |
|---|---|---|
| 공격 경로 **진입점** | 노출(LoadBalancer·Ingress·HTTPRoute)만 — 대부분 '진입 미확인' | 실행 중인 이미지의 취약성과 경로가 이어지지 않음 → **P1 (구현)** |
| Issues 단일 목록 | 클러스터 위험 조합(AKS 보안 점검) · 통합 위험 · WI-17 · Defender 경고가 화면마다 | 하나의 우선순위·상태(열림·진행·해결·예외) 없음 → **P2 (구현)** |
| 소유 | Helm 차트·kubectl로 추정 | 팀 단위 소유·필터 없음 → **P3 (구현)** |
| CIEM | RBAC 행렬 · 워크로드 ID 매핑 · IMDS 경로 | 받은 권한 대비 **실제로 쓴** 권한 없음 → **P3 (구현 — Key Vault·Storage 데이터 역할)** |
| Code-to-Cloud | KBOM(이미지·버전) | 이미지 → 저장소·커밋 연결 없음 → P4 |
| Security Graph 탐색 | 화면마다 그래프(구성도·라이브·공격 경로·네트워크 맵·WI 흐름도) | 화면을 가로지르는 질의 없음 → P5 |
| Runtime | Defender 경고 · Hubble 관측 | 경고가 경로 위에 안 보임 → P2와 함께 |
| DSPM | 없음 | 보류 — 데이터 직접 스캔은 '읽기만' 원칙과 충돌, Purview 분류 결과 읽기만 검토 |

**지킬 것(차별점)**: 근거 등급(`obs` 관측 · `perm` 권한 정의 · `cfg` 구성·스캔 · `unk` 추정·미확인). 모르는 것을 '안전'으로 칠하지 않습니다. 새 기능도 값마다 출처와 등급을 같이 냅니다.

## 3. 단계

### P0 — 같은 사실은 모든 화면에서 같은 등급 (완료, 2026-10-30)

- '상시 고권한' 조합을 히트맵과 같은 등급으로 나눔(장악 수준 = 위험 / 그 밖 = 주의), 위험순, 구성원 전부(`members`), 그래프는 8개 + '외 n개'(조용히 빼지 않음)
- 경로 머리: 한 줄 제목 → 4칸(대상 · 닿는 곳 · 끊을 곳 · 근거 — 단위 '선 n개') → 접힌 구성원 표
- 테스트: `policyInsights.test.ts` "standing privilege …", "path header …"

### P1 — 이미지 취약성 = 공격 경로의 진입점 (구현, 2026-10-30)

**왜**: 클러스터 장악 경로의 첫 칸이 '진입 미확인'이면 "정말 들어올 수 있나?"에 답하지 못합니다. 실행 중인 이미지의 미해결 CVE가 그 답의 가장 큰 부분입니다.

**출처 두 개 — 둘 다 추측이 아님** (`services/imageVulns.ts`)

| 출처 | 읽는 것 | 이미지와 잇는 규칙 | 근거 등급 |
|---|---|---|---|
| ① Defender for Containers | Resource Graph `securityresources` 하위 평가(Unhealthy) → 이미지(레지스트리·리포지토리·다이제스트·태그)별 요약 `DEFENDER_IMAGE_QUERY` | 파드 이미지의 **다이제스트**, 없으면 **태그**(같은 태그가 여러 다이제스트면 더 나쁜 쪽) | `cfg` |
| ② SBOM | 알려진 오픈소스 이미지(`sbom.ts` `KNOWN_IMAGES`)의 **정확한 semver 태그** → OSV 권고, CVE.org(CISA ADP SSVC 악용), CISA KEV | 모듈 버전 일치 — 미러·재빌드(`-dhi` 등)는 매핑하지 않음(업스트림 번호에 없는 패치가 있을 수 있음) | `cfg` |

- 합치기: 같은 이미지면 Defender(그 이미지 자체의 스캔)를 쓰고, KEV·CVE.org의 더 강한 악용 신호는 유지 (`mergeVulns`)
- 등급(`vulnWeight`): 실제 악용(KEV·CVE.org active) = 위험 · 치명/높음 = 주의 · 중간 이하·공개 익스플로잇만 = 낮음
- 스캔 결과 없는 이미지 = **'모름'** — 칸을 비우고 사실 행에 이유(Defender 결과 0건 / 이 이미지는 스캔 안 됨 / 알려진 오픈소스·정확한 버전 아님 / SBOM 조회 꺼짐)

**어디에 보이나**

1. 히트맵 12번째 요인 '취약 이미지'(노출 묶음) — 칸 = "치명 1 · 높음 3 · KEV 악용 (Defender)"
2. 공격 경로 진입 노드 — 치명·높음이 있으면 '취약 이미지'(노출도 있으면 '노출 + 취약 이미지'), 선 = `cfg` "CVE n · 악용", 카드 칩 "진입: CVE n". 없으면 '진입 미확인' + 이유(스캔됐고 치명·높음 없음도 '미확인' — 제로데이·설정 오류를 배제 못 함)
3. 워크로드 사실(상세 카드) — 상위 CVE 3개(패키지 현재 → 수정 버전, 악용 표시)
4. KBOM — 카드 '취약점(CVE)' = 치명·높음·악용이 있는 이미지 수 + '스캔 n/m · 출처', 표의 신호 열 칩

**권한·통신**: Defender는 `Security Reader`(구독) — 기능 카탈로그 `aksSecurityCheck`의 선택 권한. SBOM 조회는 긴급 취약점과 같은 외부 출처(OSV·CVE.org·CISA)와 스위치(`AUD_ADVISORY_FEEDS`·`AUD_ADVISORY_OSV`), 차트 `features.advisoryFeeds`의 CNP FQDN. 보내는 것은 오픈소스 모듈 이름·버전뿐(앱 이미지 이름은 안 보냄).

**캐시·예산**: 클러스터별 10분(조회 대기 중이면 저장 안 함). OSV 10초 · KEV 8초 · CVE.org 6초 예산 — 넘치면 다음 열기에 채움.

**한계(사실)**: 시험 환경(stg) 구독은 Defender for Containers 플랜이 켜져 있어도 Resource Graph 하위 평가가 0건이었고(2026-10-30), 앱 이미지 대부분이 미러·하드닝 재빌드라 SBOM 매핑도 적습니다 → 그 환경의 진입점은 여전히 대부분 '미확인'이지만 **이유가 보입니다**. Defender 질의는 공개 스키마 기준으로 작성하고 Resource Graph에서 실행되는 것까지 확인했으며, 실제 결과 행으로는 아직 검증하지 못했습니다.

**완료 조건**: 테스트 `imageVulns.test.ts`(다이제스트·태그 일치, 미러 비매핑, KEV 우선, 병합·등급, 질의에 테넌트 값 없음) + `policyInsights.test.ts` "entry point …"(진입 노드·12번째 요인·KBOM·이유 문구) — 충족.

### P2 — 통합 이슈 목록 + 상태·예외 (구현, 2026-10-30)

> **5살 비유**: 장난감 고장 신고가 네 군데(클러스터·ID·취약점·경보)에 따로 붙어 있었어요. 이제 **게시판 하나**에 모으고, 신고마다 "고치는 중 / 나중에(이유·날짜) / 고쳤어요" 스티커를 붙여요. 스티커를 붙여도 장난감이 아직 고장 나 있으면 게시판이 **"다시 고장"**이라고 알려 줘요.

**어디**: 보안 › 통합 위험(`/security/risk`) 맨 위 '이슈 목록' — 기존 자산 표는 그 아래 그대로.

**출처 4곳**(웹 순수 `lib/issueQueue.ts` `buildIssueQueue` — 새 수집 API 없음, 각 출처는 따로 실패하고 칩으로 상태 표시)

| 출처 | 무엇을 | 등급 | 키 |
|---|---|---|---|
| 클러스터 위험 조합 | AKS 보안 점검 `issues` | crit → 위험, warn → 높음 | `combo:<rg>/<cluster>:<조합 id>` |
| 워크로드 ID | 위험·주의 점검(WI-17 포함, 낮음·정보 제외) | crit → 위험, warn → 높음 | `wi:<rg>/<cluster>:<점검 id>` |
| 긴급 취약점 | 우리 대상에 영향(`affected`)인 것만 | KEV·실제 악용·CVSS 9 이상 → 위험, 그 밖 높음 | `vuln:<rg>/<cluster>:<공지 key>` |
| Defender 경고 | 활성 경고(정보 제외), 같은 탐지는 한 이슈 ×n | High·Medium·Low 그대로 | `alert:<심각도>:<제목 slug>` |

키는 공백 없는 ASCII(서버가 `ISSUE_KEY`로 검증), 구독 ID는 넣지 않음(저장 파일이 구독별).

**상태**(`services/issueStateStore.ts`, `GET/PUT /api/security/issue-states?subscriptionId=[&key=]`)

- 열림 · 진행 중 · 예외 · 해결 표시. 읽기 = 로그인, 쓰기 = **운영자 이상**(익명 거부), 구독 접근은 authorize 미들웨어가 먼저 확인
- **예외**: 사유(3자 이상) + 끝나는 날(내일 ~ 1년) 필수 → 그날이 지나면 화면이 '예외 만료'로 다시 엶
- **출처가 이김**: '해결 표시' 뒤에 출처가 다시 읽었는데 아직 있으면 '재발'(열림), 표시 뒤 아직 안 읽었으면 '다음 수집에서 확인'. 출처에서 사라진 이슈의 상태는 목록에 안 나오고 '더 이상 탐지 안 됨 n'(기록 보관) — 읽은 출처·지금 클러스터만 셈
- **동시 편집**: 이슈마다 `rev` — 다른 이슈는 서로 막지 않음, 같은 이슈를 먼저 바꾼 사람이 있으면 409 + 최신 값(화면이 다시 불러옴)
- **기록**: 변경 20개(시각·상태·표시 이름·메모·끝나는 날), 담당은 자유 텍스트(디렉터리 조회 안 함)
- **저장 위치**: `AUD_ISSUE_STATE_DIR` → 없으면 `<AUD_ARRANGEMENT_DIR>/issues`(온프렘은 추가 설정 없이 기존 쓰기 마운트) → 없으면 메모리(화면 경고 '서버 메모리에만 저장'). 구독마다 JSON 하나, 임시 파일 → rename, 구독별 잠금, 최대 3,000개
- **딥 링크**: 조합 이슈 → `/policies?tab=overview&cluster=…&issue=…`(그 클러스터·조합을 골라 엶), WI → 워크로드 ID 탭, 취약점 → 긴급 취약점, 경고 → 위협 탐지

**완료 조건**: `issueQueue.test.ts` — 예외 규칙, 이슈별 rev 충돌·기록 20개·키 검증, 파일 저장·기본 위치, 실효 상태(재발·확인 대기·만료), 4출처 키·등급·정렬, 탐지 안 됨 셈 — 충족.

**남은 것**: 이슈에 Defender 경고를 얹어 공격 경로 진입을 `obs`로(런타임), 이슈별 알림·티켓 연동(Teams·Jira), 팀 소유(P3)로 '내 팀' 필터.

### P3 — 팀 소유와 '받았지만 안 쓰는 권한' (구현, 2026-10-30)

> **5살 비유**: ① 장난감 상자마다 **이름표**(어느 반 것인지)를 붙여서 "우리 반 고장만 보기"가 돼요. ② 열쇠를 받았는데 한 달 동안 한 번도 안 쓴 친구는 **열쇠를 돌려주자**고 알려 줘요. 단, 문에 출입 기록장이 없으면 "안 썼다"가 아니라 "몰라요"라고 말해요.

**B. 받았지만 안 쓰는 권한(WI-18)** — 워크로드 ID 매핑의 관리 ID 역할 할당 중 **데이터 역할**(`DATA_ROLES` — Key Vault 9종·Storage 14종, **정의 ID**로 분류, 읽기/쓰기 구분)만:

| 단계 | 내용 |
|---|---|
| 읽기 | 역할 범위(리소스·RG·구독)마다 **Log Analytics 리소스 중심 조회** `POST /v1{scope}/query`, 30일 — Key Vault 감사 로그(`AzureDiagnostics` AuditEvent ∪ `AZKVAuditLogs`) / Storage 로그(`StorageBlobLogs`·File·Queue·Table). (범위, 서비스)마다 한 번, 그 범위에 역할이 있는 ID들을 함께(`roleUsageQuery` — GUID만 통과), 4개씩 동시, 10분 캐시 |

1. 이슈 카드 = **한 줄 문장 + 네 칸 요약**(대상 · 닿는 곳 · 끊을 곳 · 근거). 이름 목록은 접힌 표로 — P0에서 '상시 고권한'에 적용, 다른 조합(exfil·vnet) 제목도 같은 틀로 줄일 것
2. 그래프는 왼쪽 → 오른쪽 = 공격 방향, 같은 권한·같은 대상은 노드 하나로 묶고 '외 n개'로 생략을 밝힘
3. 숫자에는 단위('선 n개', '계정 n개', '스캔 n/m')
4. 같은 사실 = 같은 등급(히트맵 · 조합 · 경로 · KBOM), 테스트로 고정

### 5.4 Azure 위험 조합 (2026-11-17, ②)

`GET /api/security/azure-risk?subscriptionId=` → `services/azureRiskCombos.ts` → 이슈 목록 출처 `azure` + 통합 위험 화면 'Azure 위험 조합' 패널.

| 요인 | 원본 | 판정 (기존 판정기 재사용) | 모름 |
|---|---|---|---|
| 인터넷 노출 | VM: 구성도 그래프의 NSG 판정(`nsgExposure`) · PaaS: `publicNetworkAccess` + 본문 네트워크 규칙 | open = 예 · scoped(지정 출발지만) = 예 + **제한적**(등급 한 단계 낮춤) · closed·noNsg·Disabled·Deny = 아니요 · 그 밖 해당 없음 | NSG 못 읽음 · 공용 액세스 값 없음 · 규칙이 하위 리소스(SQL 등) · 그래프/쿼리 실패 |
| 높음 권고 | `securityresources` 비정상 + 심각도 High, **리소스별 전수** | 1건 이상 = 예(건수·이름 3) | 쿼리 실패 |
| 특권 ID | 리소스 `identity`(시스템·사용자 할당 → UAMI principal) → `authorizationresources` 역할 할당 | Owner·Contributor·User Access Administrator·RBAC Administrator(정의 ID) = 예 + 범위 | ID·역할 쿼리 실패 |

- 조합 = 한 리소스에 '예' 둘 이상: 노출+권고+ID 위험 · 노출+ID 높음 · 노출+권고 높음 · 권고+ID 중간 (노출이 제한적이면 한 단계 낮춤). 점수 없음.
- '예' 하나 + '모름' = **판단 불가**로 셈(조용히 빼지 않음). 요인을 못 읽은 응답(gaps)이면 저장된 이슈를 '더 이상 탐지 안 됨'으로 세지 않음.
- 이슈 키 `azure:<rg>/<공급자/유형>/<이름>`(구독 없음 — 상태 파일이 구독별). 조인은 소문자 ARM ID(이름 추측 없음). ID 파서는 중첩 유형까지(`registries/x/repositories/y`) — 한 단계만 읽던 첫 구현은 stg에서 높음 권고 리소스 699개 중 669개를 버렸음(검증에서 발견).

### 5.5 Azure 공격 경로 (2026-11-17, ③)

같은 응답(`/api/security/azure-risk`)의 `paths` → 순수 `attackPaths` → 통합 위험 화면 'Azure 공격 경로' 패널 + 데이터·특권까지 닿는 경로는 이슈(`path:<rg>/<유형>/<이름>`).

**사슬** — 근거가 있는 연결만, 끊긴 곳은 '여기서 끝남':

1. 인터넷 → **진입점**: 노출 '예'인 리소스(5.4의 노출 판정, 지정 출발지만 = 제한적)
2. → **취약점**: 그 리소스의 높음 권고(전수)
3. → **ID 역할**: 그 리소스 관리 ID(시스템·사용자 할당)의 역할, 정의 ID로 — 특권 4종 · Key Vault·Storage 데이터 역할(`DATA_ROLES`) · **키·정책 역할**(`KEY_ROLES` — Storage Account Key Operator·Storage Account Contributor = listKeys, Key Vault Contributor = 접근 정책 쓰기)
4. → **도달 데이터**: 이 구독의 Key Vault·Storage·DB(SQL·Cosmos·PostgreSQL·MySQL) 중 역할 범위 ARM ID 아래(같은 접두사의 형제 `rg`/`rg2`는 아님), 데이터 역할은 자기 서비스만

등급: 데이터·특권에 닿음 + 취약점 = 위험, 닿음만 = 높음, 진입점에서 끝남(취약점만) = 중간, 지정 출발지만 노출이면 한 단계 낮춤. 노출만 있고 취약점·도달이 없으면 경로 아님. ID·역할을 못 읽으면 `identityUnknown`('더 이어질 수 있음').

**검증·발견** (stg, 제 계정):
- 첫 구독 경로 5개 — 모두 **진입점에서 끝남**(지정 출발지만 열린 VM + 높음 권고, 관리 ID의 역할은 Reader 하나씩). 데이터까지 닿는 경로는 stg에 없어, 도달 규칙은 단위 테스트로 고정(`azureRiskCombos.test.ts` — 범위 경계·서비스 한정·키 역할·모름).
- VM 관리 ID들이 실제로 가진 역할을 이름으로 확인: Storage Blob Data Reader/Contributor · Key Vault Secrets User · Crypto User/Officer · **Storage Account Key Operator Service Role**(데이터 역할 표에 없지만 listKeys = 데이터 → `KEY_ROLES` 추가) · Reader.
- 다른 구독의 데이터는 세지 않음(구독 하나씩 읽음) — 화면 꼬리에 명시.

### 5.6 리소스 보안 카드 (2026-11-17, ④)

`GET /api/security/resource-card?resourceId=` → `services/resourceSecurityCard.ts` → 공용 컴포넌트 `components/ResourceSecurityCard.tsx`. 여는 곳: 통합 위험의 **위험 조합·공격 경로 항목**('보안 카드 ▸'), **인프라 구성도 리소스 상세**(실데이터일 때).

| 섹션 | 원본 (리소스 ID로 직접, 순차·429 재시도) | 판정 |
|---|---|---|
| Defender 권고 | 평가 — 그 리소스 + 하위 엔터티(`…/securityentitydata/…`) | 비정상·정상·해당 없음, 높음/중간/낮음, 권고별 대상 수(하위 포함 여부) |
| 활성 경고 | 경고의 `ResourceIdentifiers`가 그 리소스(또는 하위)를 가리킴 | Active·InProgress, 경고 하나 = 한 줄 |
| 인터넷 노출 | VM: 구성도 NSG 판정 · PaaS/AKS: 본문 + 하위 방화벽 규칙(`rulesExposure`) | 위험 조합과 같은 판정, 공용 엔드포인트 설정이 없는 유형 = 해당 없음 |
| 이 리소스가 할 수 있는 것 | 관리 ID(시스템·사용자 할당) principal의 역할 할당 + 역할 정의 이름(ARM, 하루 캐시) | 특권 · 데이터 · 키·정책 · 기타 |
| 누가 다룰 수 있나 | 범위가 이 리소스를 포함하는 역할 할당(관리 그룹·구독·RG·리소스 — 형제 접두사 제외) | 특권·데이터·키 역할만, 분류별 할당·주체 수 + 주체 유형·ID 끝 4자리(이름은 Graph 권한 필요) |
| 위험 조합 · 공격 경로 | 같은 키로 조인 | 칩 |

섹션마다 상태 ok · failed · na — 못 읽은 섹션은 '읽지 못함 — 없음이 아님'.

**검증** (stg, 대시보드 전체 경로 vs 같은 리소스에 대한 독립 KQL):

| 리소스 | 비정상 권고 | 활성 경고 | 관리 ID 역할 | 특권 접근 할당 |
|---|---|---|---|---|
| VM (노출+권고) | 5 = 5 | 0 = 0 | 1 = 1 | 8 = 8 |
| 컨테이너 레지스트리 (허용 목록 + 취약 이미지) | 8,889 = 8,889 | 0 = 0 | 0 = 0 | 8 = 8 |
| AKS 클러스터 (권고 + 특권 ID) | 579 = 579 | **1 = 1** | 4 = 4 | 8 = 8 |
| PostgreSQL | 2 = 2 | 0 = 0 | 0 = 0 | 8 = 8 |

검증에서 발견: 경고 조회식이 `summarize take_any(properties) by id`(잘못된 Resource Graph 쿼리), 고친 뒤에도 `distinct …, title, …`(열 이름 `title`이 파싱 실패) — 모든 카드의 경고가 '읽지 못함'이었음 → 열 이름 `dn`. 회귀 테스트로 고정.

**시험 배포 신원으로 다시 대조**(5ad5423): 위험 조합 3개(레지스트리·AKS·PostgreSQL)의 카드 = 같은 신원 독립 KQL — 비정상 권고 8,901 = 8,901 · 579 = 579 · 2 = 2, 경고 0·1·0 = 같음, 관리 ID 0·1·0 = 같음, 그 역할 0·3·0 = 같음, 특권 접근 0·0·0 = 같음, 익명 401.
**거기서 발견 — 보이지 않는 것을 '없음'으로 말함**: 배포 신원은 리소스 그룹 Reader라 Resource Graph의 역할 할당이 **리소스 그룹·리소스 수준 46개뿐**(구독·관리 그룹 수준 0 — 내 토큰은 구독 수준 포함 8개). 그 상태로 카드는 '특권 할당 없음', 위험 조합은 '특권 역할 없음(아니요)', 공격 경로는 '여기서 끝남'이라고 말했음 — 구독 Owner가 있어도 안 보이는데. 고침: 구독·관리 그룹 수준 할당이 하나도 안 보이면(`ABOVE_Q` 한 줄 확인, 카드는 이미 읽은 행으로) 카드 두 역할 절에 '구독 수준은 보이지 않음 — 보이는 범위(RG·리소스)에는 없음', 위험 조합의 '특권 역할 없음' → 판단 불가 `rolesAboveHidden`(관리 ID 없음은 그대로 '아니요'), 공격 경로 `identityUnknown`('구독 수준 역할이 보이지 않아 더 이어지는지 모름'). 응답 `rolesAboveHidden`·카드 `access.aboveHidden`. 구독 Reader를 주면 사라짐.

### 5.7 보안 개요 팀 범위 (2026-11-17, ⑤)

`GET /api/security/team-scope?subscriptionId=` → `services/securityTeamScope.ts`(리소스 그룹마다 원시 개수만) → 웹 순수 `lib/teamScope.ts`(`teamScopeView`)가 **이슈 목록과 같은 `teamOf`**로 팀에 나눔 → 보안 개요의 '범위' 선택 + '팀별 요약' 표. 고른 팀은 이슈 목록과 같은 브라우저 키(`aud.issues.team`) — 한 번 고르면 두 화면이 같은 팀.

| 무엇 | 원본 (순차 읽기 4개) | 팀으로 나뉘나 |
|---|---|---|
| 영향 리소스(높음·중간·낮음) | 평가 비정상 — `summarize by rid, rg, sev \| summarize count() by rg, sev` (**정확한 개수**) | 예 — 리소스는 그룹 하나에만 있어 팀 값 = 그룹 값의 합 |
| 권고 발견 · 영역별 · 우선 조치 | 평가 비정상 `count() by rg, key, sev` (영역·제목은 개요 응답의 같은 키) | 예 |
| 활성 경고 | 경고의 `ResourceIdentifiers` → 리소스 그룹 묶음(경고 ID는 응답에 없음) | 예 — 두 팀 리소스를 가리키면 두 팀에 셈(표 꼬리에 개수) |
| 리소스 수 | `resources` 그룹별 개수 | 예 |
| 보안 점수 · 컨트롤 · 규정 준수 · 플랜 | 구독 수준 리소스 | **아니요** — 팀을 고르면 '구독 전체 값'이라고 표시 |

- 규칙: 리소스 그룹 규칙만(이슈 목록의 순서 — 첫 일치). 네임스페이스 규칙은 클러스터 안 이슈용 — 네임스페이스 규칙만 있는 팀은 이 화면에서 '—'(0 아님)과 이유.
- 버킷: 팀(파일 순서, 같은 팀 여러 규칙 = 하나) · 소유 미지정 · 리소스 그룹 없음(구독 자체의 평가, Azure 리소스를 가리키지 않는 경고) — 모든 그룹이 정확히 하나에 들어가 **합 = 구독 전체**(테스트).
- 못 읽은 부분 = 그 열 '—'(0 아님), 1만 행 상한에 닿으면 gap.
- 함께 고침: 개요의 '영향 리소스' KPI가 `dcount`(추정치)였음 → 정확한 개수(`summarize by` 뒤 `count`).
**검증** (실데이터, 실제 그룹 이름으로 만든 규칙 — A = 정확한 이름 2개 · B = 여러 그룹에 맞는 접두사(A와 겹침 → 첫 규칙 우선) · C = 네임스페이스만 / 독립 KQL = 평가 자체의 `resourceGroup` 열(ID 파싱 아님)):

| | 높음/중간/낮음 영향 리소스 · 권고 발견 · 활성 경고 |
|---|---|
| 구독 1 (그룹 24, B = 15그룹) | A 662/471/484 · 10,721 · 2 = · B 37/70/54 · 986 · 0 = · 전체 700/541/538 · 11,714 · 2 = |
| 구독 2 (그룹 12, B = 5그룹) | A 7/15/13 · 604 · 0 = · B 0/2/8 · 13 · 4 = · 전체 14/27/21 · 635 · 4 = |
| 구독 3 (그룹 4) | A 5/11/9 · 33 = · B 0(맞는 그룹이 모두 A — 첫 규칙 우선) = · 전체 6/12/10 · 42 = |
| 시험 배포 신원 (그룹 3) | 영향·발견 = · 개요 KPI(정확한 개수) = 팀 범위 합계 572/419/422 · **경고 1건이 '그룹 없음'으로 감 ≠** |

검증에서 발견: 경고의 `AzureResourceId`는 `/resourceGroups/`(대문자)인데 소문자 정규식을 원문에 적용 → 모든 경고가 '리소스 그룹 없음'. 소문자로 바꾼 뒤 추출하도록 고침 + 회귀 테스트(모든 `extract`가 소문자 값을 읽는지).
**보안 권고 · ID·권한 · 위협 탐지에도 같은 범위**(2026-11-17): 팀 선택·팀 범위 응답은 보안 레이아웃의 공용 상태(`SecurityContext` `team`, 이 네 화면에서만 읽음) — 화면마다 '범위' 막대(`TeamScopeBar`). 보안 권고·ID·권한 = 그 팀 리소스 그룹에 발견이 있는 권고만, 건수 = 그 팀의 발견(`recsInBucket` — 정상 수는 팀으로 나누지 않아 'n / 전체' 대신 '발견 n건'), 예시 리소스도 그 팀 것만. 위협 탐지 = 그 팀 리소스를 가리키는 경고(`alertBuckets` — API와 같은 규칙, 두 팀이면 둘 다), 목록은 최근 200건이라 팀 전체 수가 더 많으면 '목록 n건 · 팀 전체 m건'.
검증(실데이터, 구독 3개 × 팀 2개 — A = 가장 바쁜 그룹, B = 나머지): 권고 행마다 (키, 심각도)의 팀 발견 수 = 독립 KQL `count() by name, severity` — 다른 행 0, 행 수·합 같음(구독 1: A 276행 Σ 9,516 · B 239행 Σ 2,197), 경고 목록 = 팀 범위 = 독립 집계(1·1 / 0·4 / 0·0).
검증에서 발견: Defender는 **같은 권고 키를 심각도별로 따로** 줌(개요는 키·제목·심각도로 묶음 — 구독 1에서 259키 = 280행) → 키로만 맞추면 팀 건수가 두 행에 붙어 Σ 11,151(팀 발견 9,516). (키, 심각도)로 맞춤(`recId`) — 개요의 '우선 조치 권고'·영역별 종류 수도 같은 원인이었음, 회귀 테스트.
- 시험 배포의 팀 규칙은 네임스페이스 규칙 2개뿐 → 화면은 '모두 소유 미지정 — 리소스 그룹 규칙을 넣으면 나뉨' + 연결 파일 예(복사).
