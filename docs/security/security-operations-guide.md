# 보안 기능 운영 가이드 — 이슈 목록 · 위험 조합 · 워크로드 ID

운영자·보안 담당자가 **매일 보는 순서**와 **화면의 말을 읽는 법**을 적은 문서입니다. 왜 이렇게 만들었는지(설계·단계·실측)는 [보안 고도화 계획](../architecture/security-roadmap.md), 권한은 [permissions.md](../integrations/azure/permissions.md), 오류 코드는 [error-catalog §6](../troubleshooting/error-catalog.md#6-보안-defender-for-cloud)에 있습니다.

> **5살 비유**: 우리 집 지키기예요. ① 게시판(이슈 목록)에서 오늘 고칠 일을 고르고 ② 도둑이 들어올 길(위험 조합)을 그림으로 보고 ③ 문(진입점)·열쇠(권한)·보물(닿는 곳) 중 **가장 쉬운 고리를 끊어요**. 모르는 것은 "괜찮아요"가 아니라 "몰라요"라고 적혀 있어요.

## 1. 매일 하는 순서

| 순서 | 화면 | 할 일 |
|---|---|---|
| 1 | 보안 › **통합 위험** › 이슈 목록 | 상태 '열림·진행', 팀 = 내 팀 → 위에서부터(위험 → 높음 → …) |
| 2 | 이슈 펼치기 → '…에서 보기' | 원래 화면(AKS 보안 점검·워크로드 ID·긴급 취약점·위협 탐지)으로 이동 |
| 3 | AKS 보안 점검 › 위험 조합 | 제목 아래 4칸으로 판단 → 조치(안전/주의)·**고칠 곳** → 티켓 복사 |
| 4 | 이슈 목록 | 상태 바꾸기: 진행 중 / 예외(사유·끝나는 날) / 해결 표시 |
| 5 | 다음 날 | '재발'·'예외 만료' 표시가 붙은 이슈부터 |

## 2. 이슈 목록 (보안 › 통합 위험)

### 2.1 무엇이 모이나 — 출처 4곳

| 출처 | 들어오는 것 | 등급 |
|---|---|---|
| 클러스터 위험 조합 | AKS 보안 점검의 공격 경로(유출·장악·노출·상시 고권한·로컬 계정) | 위험 / 높음 |
| 워크로드 ID | 위험·주의 점검(WI-17 IMDS 경로, WI-18 안 쓰는 권한 포함) — 낮음·참고는 빠짐 | 위험 / 높음 |
| 긴급 취약점 | 우리 대상(대시보드 런타임·클러스터 이미지)에 **영향 있음**인 공지만 | 실제 악용·CVSS 9 이상 = 위험, 그 밖 높음 |
| Defender 경고 | 활성 경고(정보 제외) — 같은 탐지는 한 이슈 ×n | 높음 / 중간 / 낮음 |

화면 위 칩이 출처마다 **읽음 · 읽는 중 · 읽지 못함 · 해당 없음**을 보여 줍니다. 한 출처가 실패해도 나머지는 그대로 나옵니다 — 칩이 '읽지 못함'이면 그 출처의 이슈는 **없는 것이 아니라 못 본 것**입니다.

### 2.2 상태 규칙

| 상태 | 뜻 | 규칙 |
|---|---|---|
| 열림 | 아직 아무도 손대지 않음 | 기본값 |
| 진행 중 | 누군가 고치는 중 | 담당(사람·팀 이름, 자유 글)·메모 |
| 예외 | 지금은 고치지 않기로 함 | **사유(3자 이상) + 끝나는 날(내일 ~ 1년)** 필수 → 그날이 지나면 **'예외 만료'로 다시 열림** |
| 해결 표시 | 고쳤다고 표시 | 출처가 **표시 뒤에 다시 읽었는데 아직 있으면 '재발'(열림)**, 아직 다시 안 읽었으면 '다음 수집에서 확인' |

- **출처가 이깁니다**: 이슈 자체는 매번 출처에서 다시 계산하고, 저장하는 것은 팀이 정한 상태뿐입니다. 출처에서 사라진 이슈의 상태는 목록에 나오지 않고 '더 이상 탐지 안 됨 n'으로만 셉니다(기록은 남음).
- **누가**: 읽기 = 로그인한 사용자, 바꾸기 = **운영자(AUD.Operator) 이상**. 변경 기록 20개(시각·표시 이름·상태·메모·끝나는 날)가 이슈마다 남습니다.
- **동시에 바꾸면**: 다른 이슈끼리는 서로 막지 않습니다. 같은 이슈를 그사이 다른 사람이 바꿨으면 "그사이 다른 사람이 바꿨습니다"와 함께 최신 값을 다시 불러옵니다 — 확인하고 다시 저장하세요.

### 2.3 팀(소유) 설정

연결 파일([connect-tenant.md](../integrations/azure/connect-tenant.md)의 `owners`)에 팀 → 네임스페이스·리소스 그룹을 적으면 이슈마다 팀 칩이 붙고 '팀' 필터가 생깁니다.

```json
"owners": [
  { "team": "platform", "namespaces": ["kube-system", "monitor", "argocd"] },
  { "team": "payments", "namespaces": ["pay-*"], "resourceGroups": ["rg-pay-*"] }
]
```

- **네임스페이스 규칙이 리소스 그룹 규칙보다 먼저**, 같은 종류는 파일에 적힌 순서로 처음 맞는 팀. 이름은 정확히(대소문자 무시) 또는 끝 `*`(접두사)
- 이슈의 네임스페이스는 출처에서: 위험 조합 = 구성원·워크로드, 워크로드 ID = 점검 대상 워크로드·SA, 긴급 취약점 = 영향 받는 워크로드, Defender 경고 = K8s 네임스페이스·리소스 그룹. 네임스페이스가 없으면 클러스터의 리소스 그룹
- '내 팀'은 디렉터리로 찾지 않습니다 — 화면에서 고르면 그 브라우저에만 기억됩니다
- 팀 이름만 적습니다(사람 이름·ID 금지 — GUID는 거부). 잘못 적으면 API가 시작하지 않습니다([CONN-010](../troubleshooting/error-catalog.md#conn-010-연결-파일-owners-오류로-api가-시작하지-않음))

### 2.4 상태가 어디에 저장되나

`AUD_ISSUE_STATE_DIR` → 없으면 `<AUD_ARRANGEMENT_DIR>/issues` → 둘 다 없으면 **API 메모리**(화면에 '상태가 서버 메모리에만 저장됩니다' 경고, 재시작하면 사라짐). 온프렘 Docker는 기존 쓰기 마운트(`state/arrangements`) 안 `issues/`를 써서 추가 설정이 없습니다. 쿠버네티스는 쓰기 볼륨을 붙이고 위 변수 중 하나를 넣으세요([kubernetes.md](../deployment/kubernetes.md)). 무엇이 저장되는지는 [data-collected.md](../integrations/azure/data-collected.md)의 '이슈 상태'.

## 3. 위험 조합 읽는 법 (AKS 보안 점검 › 위험 개요)

### 3.1 제목 아래 4칸

| 칸 | 뜻 | 예 |
|---|---|---|
| 대상 | 워크로드 n개 또는 서비스 계정 n개(그중 장악 수준 k) | 서비스 계정 3개 |
| 닿는 곳 | 경로의 끝(영향) | 클러스터 전체 · 노드 5대의 파드 163개 |
| 끊을 곳 | 차단 지점 수 · 안전한 조치 수 | 3곳 · 안전한 조치 3 |
| 근거 | **선(연결) 개수**와 종류 | 선 5개 모두 RBAC 권한 / 선 6개 — 관측 2 · 권한 3 · 추정 1 |

'확인 안 된 고리 n'이 있으면 그만큼은 **추론**입니다 — 그 선은 회색 점선으로 그려집니다.

### 3.2 근거 등급 (선의 색과 칩)

| 등급 | 무엇으로 확인했나 |
|---|---|
| 관측 `obs` | 실제로 일어난 것 — Hubble 흐름, 접근 로그(Key Vault·Storage), Defender 경고 |
| 권한 `perm` | RBAC 정의상 가능한 것(실제로 했는지는 아님) |
| 구성 `cfg` | 매니페스트·Azure 설정·스캔 결과 |
| 추정·미확인 `unk` | 데이터가 없어 추론한 것 — 위험 색을 칠하지 않음 |

### 3.3 상시 고권한 계정

토큰이 늘 붙어 있는 서비스 계정의 위험 권한입니다. **히트맵과 같은 기준**으로 두 장으로 나뉩니다 — 클러스터 장악 수준(cluster-admin · bind/escalate · impersonate · Webhook 변경 · nodes/proxy) = **위험**, 그 밖(Secret 조회 · exec · 토큰 발급 등) = **주의**. 그래프는 위험순 8개까지 그리고 나머지는 '외 n개' 노드에 이름이 있습니다. 전원은 '구성원 n개 전부 보기' 표에 있고, 이름을 누르면 히트맵 행으로 갑니다.

### 3.4 진입점 — 취약 이미지

경로 첫 칸(진입)은 노출(LoadBalancer·Ingress 등)과 **실행 중인 이미지의 취약성**으로 정합니다. 치명·높음 CVE가 있으면 '취약 이미지'(노출도 있으면 '노출 + 취약 이미지'), 없으면 '진입 미확인' + 이유. 이유는 §7 표를 보세요. 이미지 취약성은 §4.

### 3.5 조치와 '고칠 곳'

조치마다 **수정 위험**(안전 / 주의 / 중단 위험)과 효과(해결하는 점검 수·끊는 선)가 붙습니다. 워크로드가 Argo CD로 배포되면 **'고칠 곳: Argo CD 앱 → 저장소/경로 @브랜치 · values: …'**가 붙습니다(§6) — 클러스터에서 직접 고치지 말고 그 저장소에서 고치세요(GitOps가 되돌립니다). 체크하면 그래프·판정 숫자에 바로 반영되고, '티켓' 탭에서 문구를 복사합니다.

## 4. 이미지 취약성 (진입점·KBOM)

| 출처 | 읽는 것 | 이미지와 잇는 규칙 |
|---|---|---|
| Defender for Containers | 레지스트리·실행 이미지 취약성 결과(Resource Graph) | 파드 이미지의 다이제스트, 없으면 태그 |
| SBOM | 알려진 오픈소스 이미지(cilium·argo-cd·coredns·loki 등)의 **정확한 버전** → OSV · CVE.org · CISA KEV | 모듈 버전 일치 — 미러·재빌드(`-dhi` 등)는 매핑하지 않음 |

- 등급: 실제 악용(CISA KEV · CVE.org active) = **위험**, 치명·높음 = **주의**
- **스캔 결과가 없는 이미지 = '모름'**(깨끗하다는 뜻이 아님) — 히트맵 '취약 이미지' 칸이 비고, 워크로드 상세에 이유가 적힘
- KBOM 카드 '취약점(CVE)': 치명·높음·악용 이미지 수 + '스캔 n/m · 출처'. 출처를 하나도 읽지 못하면 '—'(0 아님)
- 밖으로 나가는 것: OSV에 **오픈소스 모듈 이름·버전만**(앱 이미지 이름·테넌트 정보는 보내지 않음). 끄기: `AUD_ADVISORY_OSV=false`(조회만) / `AUD_ADVISORY_FEEDS=false`(외부 전부)
- Defender 결과가 0건이면: 구독의 Defender for Containers 플랜과 '레지스트리 취약성 평가' 확장, 레지스트리 종류(ACR)를 확인하세요. 플랜이 켜져 있어도 결과가 0건일 수 있습니다(시험 환경 실측) — 그때도 화면은 '모름'으로 정직하게 남습니다

## 5. 워크로드 ID — WI-17 · WI-18 (AKS 보안 점검 › ID·권한 › 워크로드 ID)

### 5.1 WI-17 — 노드 풀에 붙은 관리 ID (IMDS 경로)

관리 ID가 노드 풀 VMSS에 붙어 있고 파드의 IMDS(169.254.169.254) 접근이 막혀 있지 않으면, **그 노드에서 도는 모든 파드**가 워크로드 ID 없이 그 ID의 토큰을 받을 수 있습니다. 흐름도 '토큰 경로' 열의 노드 풀 카드(주황 점선)가 이 경로입니다 — 어느 워크로드가 실제로 쓰는지는 선으로 긋지 않습니다(호출 IP가 노드라 구분 불가). 아래 '워크로드 ID를 쓰지 않는 워크로드' 표가 후보입니다.

조치 순서: ① 그 ID가 필요한 워크로드를 워크로드 ID로 옮기기 → ② VMSS에 붙인 출처(IaC·스크립트)에서 떼기 → ③ IMDS가 필요 없는 네임스페이스는 169.254.169.254 송신 차단(①보다 먼저 막으면 앱이 멈춤). **AKS가 붙인 ID**(노드 리소스 그룹 — kubelet·추가 기능)는 떼지 말고 역할만 줄이세요. 클러스터 단위 IMDS 제한(미리 보기)은 Container Insights·Azure Policy 같은 추가 기능이 켜져 있으면 쓸 수 없습니다 — 카드에 그 이유가 나옵니다.

### 5.2 WI-18 — 받았지만 안 쓰는 권한

관리 ID의 Key Vault·Storage **데이터 역할**이 실제로 쓰였는지, **역할 범위의 접근 로그**(최근 30일)로 판정합니다.

| 화면 | 뜻 | 할 일 |
|---|---|---|
| 사용 n회 · 마지막 날짜 | 이 ID의 요청이 있음 | — |
| **30일 미사용** — 같은 범위 다른 요청 n건 | 로그는 쌓이는데 이 ID의 요청만 0 | 아래 확인 뒤 역할 지우기(쓰기 역할이면 주의, 읽기면 낮음) |
| 확인 불가 — 접근 로그 없음 | 그 범위의 Key Vault·Storage 로그가 Log Analytics에 없음 | 진단 설정(AuditEvent / Storage 로그 → 작업 영역) 확인 |
| 확인 불가 — 권한 없음 | 로그를 읽을 권한이 없음 | 범위에 Reader(리소스 로그 읽기 포함), 작업 영역 접근 모드 '리소스 또는 작업 영역 권한' |
| 확인 불가 — 기록하는 로그 없음 | 제어 평면 역할(Contributor 등 — 읽기는 Activity Log에 안 남음)·AcrPull·관리 그룹 범위 | 판정하지 않음 |

**지우기 전에**: 월말·분기 배치처럼 30일보다 드물게 쓰는 작업이 있는지, 로그 보존 기간이 30일보다 짧지 않은지, 같은 ID가 다른 범위의 역할로 같은 리소스를 쓰는지 확인하세요. 예: Key Vault CSI 드라이버를 워크로드 ID 모드로 쓰면 **추가 기능 ID의 Key Vault 역할은 쓰이지 않아** WI-18로 나옵니다 — 이 경우 지워도 됩니다.

## 6. 배포 출처 · 고칠 곳 (Argo CD)

클러스터의 Argo CD `Application`을 읽어, 그 앱의 `status.resources`(Argo CD가 관리한다고 적은 목록)에 **정확히 있는** 워크로드만 연결합니다 — 이름·라벨로 짐작하지 않습니다.

- 보이는 곳: 워크로드 상세 '배포 출처', 위험 조합 조치 '고칠 곳', KBOM '배포 출처' 열
- 저장소 주소에서 사용자 정보·토큰·쿼리를 지우고 보여 줍니다
- **안 보이면**: KBOM에 '배포 출처를 읽을 권한이 없습니다'가 나오면 클러스터 읽기 역할에 `applications.argoproj.io` list가 없는 것입니다 — 갱신된 [`aud-dashboard-reader.yaml`](../integrations/azure/templates/aks/aud-dashboard-reader.yaml)을 적용하세요([aks.md](../integrations/azure/aks.md)). Argo CD가 없는 클러스터는 아무 표시가 없습니다
- 이미지 → 소스 코드(저장소·커밋)는 아직 아님: 이미지에 OCI 라벨 `org.opencontainers.image.source`·`revision`이 있어야 하고(빌드 시 `--label`), 읽으려면 레지스트리 권한이 필요해 보류 중입니다([로드맵 P4b](../architecture/security-roadmap.md))
