# 보안 기능 운영 가이드 — 이슈 목록 · 위험 조합 · 워크로드 ID

운영자·보안 담당자가 **매일 보는 순서**와 **화면의 말을 읽는 법**을 적은 문서입니다. 왜 이렇게 만들었는지(설계·단계·실측)는 [보안 고도화 계획](../architecture/security-roadmap.md), 권한은 [permissions.md](../integrations/azure/permissions.md), 오류 코드는 [error-catalog §6](../troubleshooting/error-catalog.md#6-보안-defender-for-cloud)에 있습니다.

> **5살 비유**: 우리 집 지키기예요. ① 게시판(이슈 목록)에서 오늘 고칠 일을 고르고 ② 도둑이 들어올 길(위험 조합)을 그림으로 보고 ③ 문(진입점)·열쇠(권한)·보물(닿는 곳) 중 **가장 쉬운 고리를 끊어요**. 모르는 것은 "괜찮아요"가 아니라 "몰라요"라고 적혀 있어요.

## 1. 매일 하는 순서

| 순서 | 화면 | 할 일 |
|---|---|---|
| 1 | 보안 › **통합 위험** › 이슈 목록 | 상태 '열림·진행', 팀 = 내 팀 → 위에서부터(위험 → 높음 → …) |
| 2 | 이슈 펼치기 → '…에서 보기' | 원래 화면(AKS 보안 점검·워크로드 ID·긴급 취약점·위협 탐지)으로 이동 |
| 3 | AKS 보안 점검 › 위험 조합 | 제목 아래 4칸으로 판단 → 조치(안전/주의)·**고칠 곳** → 티켓 복사 |
| 4 | 이슈 목록 | 상태 바꾸기: 진행 중 / 예외(사유·끝나는 날) / 해결 표시 |
| 5 | 다음 날 | '재발'·'예외 만료' 표시가 붙은 이슈부터 |

## 2. 이슈 목록 (보안 › 통합 위험)

### 2.1 무엇이 모이나 — 출처 5곳

| 출처 | 들어오는 것 | 등급 |
|---|---|---|
| 클러스터 위험 조합 | AKS 보안 점검의 공격 경로(유출·장악·노출·상시 고권한·로컬 계정) | 위험 / 높음 |
| 워크로드 ID | 위험·주의 점검(WI-17 IMDS 경로, WI-18 안 쓰는 권한 포함) — 낮음·참고는 빠짐 | 위험 / 높음 |
| 긴급 취약점 | 우리 대상(대시보드 런타임·클러스터 이미지)에 **영향 있음**인 공지만 | 실제 악용·CVSS 9 이상 = 위험, 그 밖 높음 |
| Defender 경고 | 활성 경고(정보 제외) — 같은 탐지는 한 이슈 ×n | 높음 / 중간 / 낮음 |
| 감시 질문 | 그래프 탐색(§7)의 팀 질문 중 '감시'인 것 — 모든 조건이 '예'인 워크로드마다 이슈 하나(판단 불가는 안 올림) | 질문에 정한 등급(위험·높음·중간) |

화면 위 칩이 출처마다 **읽음 · 읽는 중 · 읽지 못함 · 해당 없음**을 보여 줍니다. 한 출처가 실패해도 나머지는 그대로 나옵니다 — 칩이 '읽지 못함'이면 그 출처의 이슈는 **없는 것이 아니라 못 본 것**입니다.

### 2.2 상태 규칙

| 상태 | 뜻 | 규칙 |
|---|---|---|
| 열림 | 아직 아무도 손대지 않음 | 기본값 |
| 진행 중 | 누군가 고치는 중 | 담당(사람·팀 이름, 자유 글)·메모 |
| 예외 | 지금은 고치지 않기로 함 | **사유(3자 이상) + 끝나는 날(내일 ~ 1년)** 필수 → 그날이 지나면 **'예외 만료'로 다시 열림** |
| 해결 표시 | 고쳤다고 표시 | 출처가 **표시 뒤에 다시 읽었는데 아직 있으면 '재발'(열림)**, 아직 다시 안 읽었으면 '다음 수집에서 확인' |

- **출처가 이깁니다**: 이슈 자체는 매번 출처에서 다시 계산하고, 저장하는 것은 팀이 정한 상태뿐입니다. 출처에서 사라진 이슈의 상태는 목록에 나오지 않고 '더 이상 탐지 안 됨 n'으로만 셉니다(기록은 남음).
- **누가**: 읽기 = 로그인한 사용자, 바꾸기 = **운영자(AUD.Operator) 이상**. 변경 기록 20개(시각·표시 이름·상태·메모·끝나는 날)가 이슈마다 남습니다.
- **동시에 바꾸면**: 다른 이슈끼리는 서로 막지 않습니다. 같은 이슈를 그사이 다른 사람이 바꿨으면 "그사이 다른 사람이 바꿨습니다"와 함께 최신 값을 다시 불러옵니다 — 확인하고 다시 저장하세요.

### 2.3 팀(소유) 설정

연결 파일([connect-tenant.md](../integrations/azure/connect-tenant.md)의 `owners`)에 팀 → 네임스페이스·리소스 그룹을 적으면 이슈마다 팀 칩이 붙고 '팀' 필터가 생깁니다.

```json
"owners": [
  { "team": "platform", "namespaces": ["kube-system", "monitor", "argocd"] },
  { "team": "payments", "namespaces": ["pay-*"], "resourceGroups": ["rg-pay-*"] }
]
```

- **네임스페이스 규칙이 리소스 그룹 규칙보다 먼저**, 같은 종류는 파일에 적힌 순서로 처음 맞는 팀. 이름은 정확히(대소문자 무시) 또는 끝 `*`(접두사)
- 이슈의 네임스페이스는 출처에서: 위험 조합 = 구성원·워크로드, 워크로드 ID = 점검 대상 워크로드·SA, 긴급 취약점 = 영향 받는 워크로드, Defender 경고 = K8s 네임스페이스·리소스 그룹. 네임스페이스가 없으면 클러스터의 리소스 그룹
- '내 팀'은 디렉터리로 찾지 않습니다 — 화면에서 고르면 그 브라우저에만 기억됩니다
- 팀 이름만 적습니다(사람 이름·ID 금지 — GUID는 거부). 잘못 적으면 API가 시작하지 않습니다([CONN-010](../troubleshooting/error-catalog.md#conn-010-연결-파일-owners-오류로-api가-시작하지-않음))

### 2.4 상태가 어디에 저장되나

`AUD_ISSUE_STATE_DIR` → 없으면 `<AUD_ARRANGEMENT_DIR>/issues` → 둘 다 없으면 **API 메모리**(화면에 '상태가 서버 메모리에만 저장됩니다' 경고, 재시작하면 사라짐). 온프렘 Docker는 기존 쓰기 마운트(`state/arrangements`) 안 `issues/`를 써서 추가 설정이 없습니다. 쿠버네티스는 쓰기 볼륨을 붙이고 위 변수 중 하나를 넣으세요([kubernetes.md](../deployment/kubernetes.md)). 무엇이 저장되는지는 [data-collected.md](../integrations/azure/data-collected.md)의 '이슈 상태'.

## 3. 위험 조합 읽는 법 (AKS 보안 점검 › 위험 개요)

### 3.1 제목 아래 4칸

| 칸 | 뜻 | 예 |
|---|---|---|
| 대상 | 워크로드 n개 또는 서비스 계정 n개(그중 장악 수준 k) | 서비스 계정 3개 |
| 닿는 곳 | 경로의 끝(영향) | 클러스터 전체 · 노드 5대의 파드 163개 |
| 끊을 곳 | 차단 지점 수 · 안전한 조치 수 | 3곳 · 안전한 조치 3 |
| 근거 | **선(연결) 개수**와 종류 | 선 5개 모두 RBAC 권한 / 선 6개 — 관측 2 · 권한 3 · 추정 1 |

'확인 안 된 고리 n'이 있으면 그만큼은 **추론**입니다 — 그 선은 회색 점선으로 그려집니다.

### 3.2 근거 등급 (선의 색과 칩)

| 등급 | 무엇으로 확인했나 |
|---|---|
| 관측 `obs` | 실제로 일어난 것 — Hubble 흐름, 접근 로그(Key Vault·Storage), Defender 경고 |
| 권한 `perm` | RBAC 정의상 가능한 것(실제로 했는지는 아님) |
| 구성 `cfg` | 매니페스트·Azure 설정·스캔 결과 |
| 추정·미확인 `unk` | 데이터가 없어 추론한 것 — 위험 색을 칠하지 않음 |

### 3.3 상시 고권한 계정

토큰이 늘 붙어 있는 서비스 계정의 위험 권한입니다. **히트맵과 같은 기준**으로 두 장으로 나뉩니다 — 클러스터 장악 수준(cluster-admin · bind/escalate · impersonate · Webhook 변경 · nodes/proxy) = **위험**, 그 밖(Secret 조회 · exec · 토큰 발급 등) = **주의**. 그래프는 위험순 8개까지 그리고 나머지는 '외 n개' 노드에 이름이 있습니다. 전원은 '구성원 n개 전부 보기' 표에 있고, 이름을 누르면 히트맵 행으로 갑니다.

### 3.4 진입점 — 취약 이미지

경로 첫 칸(진입)은 노출(LoadBalancer·Ingress 등)과 **실행 중인 이미지의 취약성**으로 정합니다. 치명·높음 CVE가 있으면 '취약 이미지'(노출도 있으면 '노출 + 취약 이미지'), 없으면 '진입 미확인' + 이유. 이유는 §7 표를 보세요. 이미지 취약성은 §4.

### 3.5 조치와 '고칠 곳'

조치마다 **수정 위험**(안전 / 주의 / 중단 위험)과 효과(해결하는 점검 수·끊는 선)가 붙습니다. 워크로드가 Argo CD로 배포되면 **'고칠 곳: Argo CD 앱 → 저장소/경로 @브랜치 · values: …'**가 붙습니다(§6) — 클러스터에서 직접 고치지 말고 그 저장소에서 고치세요(GitOps가 되돌립니다). 체크하면 그래프·판정 숫자에 바로 반영되고, '티켓' 탭에서 문구를 복사합니다.

## 4. 이미지 취약성 (진입점·KBOM)

| 출처 | 읽는 것 | 이미지와 잇는 규칙 |
|---|---|---|
| Defender for Containers | 레지스트리·실행 이미지 취약성 결과(Resource Graph) | 파드 이미지의 다이제스트, 없으면 태그 |
| SBOM | 알려진 오픈소스 이미지(cilium·argo-cd·coredns·loki 등)의 **정확한 버전** → OSV · CVE.org · CISA KEV | 모듈 버전 일치 — 미러·재빌드(`-dhi` 등)는 매핑하지 않음 |

- 등급: 실제 악용(CISA KEV · CVE.org active) = **위험**, 치명·높음 = **주의**
- **스캔 결과가 없는 이미지 = '모름'**(깨끗하다는 뜻이 아님) — 히트맵 '취약 이미지' 칸이 비고, 워크로드 상세에 이유가 적힘
- KBOM 카드 '취약점(CVE)': 치명·높음·악용 이미지 수 + '스캔 n/m · 출처'. 출처를 하나도 읽지 못하면 '—'(0 아님)
- 밖으로 나가는 것: OSV에 **오픈소스 모듈 이름·버전만**(앱 이미지 이름·테넌트 정보는 보내지 않음). 끄기: `AUD_ADVISORY_OSV=false`(조회만) / `AUD_ADVISORY_FEEDS=false`(외부 전부)
- Defender 결과가 0건이면: 구독의 Defender for Containers 플랜과 '레지스트리 취약성 평가' 확장, 레지스트리 종류(ACR)를 확인하세요. 플랜이 켜져 있어도 결과가 0건일 수 있습니다(시험 환경 실측) — 그때도 화면은 '모름'으로 정직하게 남습니다

## 5. 워크로드 ID — WI-17 · WI-18 · WI-19 (AKS 보안 점검 › ID·권한 › 워크로드 ID)

### 5.1 WI-17 — 노드 풀에 붙은 관리 ID (IMDS 경로)

관리 ID가 노드 풀 VMSS에 붙어 있고 파드의 IMDS(169.254.169.254) 접근이 막혀 있지 않으면, **그 노드에서 도는 모든 파드**가 워크로드 ID 없이 그 ID의 토큰을 받을 수 있습니다. 흐름도 '토큰 경로' 열의 노드 풀 카드(주황 점선)가 이 경로입니다 — 어느 워크로드가 실제로 쓰는지는 선으로 긋지 않습니다(호출 IP가 노드라 구분 불가). 아래 '워크로드 ID를 쓰지 않는 워크로드' 표가 후보입니다.

조치 순서: ① 그 ID가 필요한 워크로드를 워크로드 ID로 옮기기 → ② VMSS에 붙인 출처(IaC·스크립트)에서 떼기 → ③ IMDS가 필요 없는 네임스페이스는 169.254.169.254 송신 차단(①보다 먼저 막으면 앱이 멈춤). **AKS가 붙인 ID**(노드 리소스 그룹 — kubelet·추가 기능)는 떼지 말고 역할만 줄이세요. 클러스터 단위 IMDS 제한(미리 보기)은 Container Insights·Azure Policy 같은 추가 기능이 켜져 있으면 쓸 수 없습니다 — 카드에 그 이유가 나옵니다.

### 5.2 WI-18 — 받았지만 안 쓰는 권한

관리 ID의 Key Vault·Storage **데이터 역할**이 실제로 쓰였는지, **역할 범위의 접근 로그**(최근 30일)로 판정합니다.

| 화면 | 뜻 | 할 일 |
|---|---|---|
| 사용 n회 · 마지막 날짜 | 이 ID의 요청이 있음 | — |
| **30일 미사용** — 같은 범위 다른 요청 n건 | 로그는 쌓이는데 이 ID의 요청만 0 | 아래 확인 뒤 역할 지우기(쓰기 역할이면 주의, 읽기면 낮음) |
| 확인 불가 — 접근 로그 없음 | 그 범위의 Key Vault·Storage 로그가 Log Analytics에 없음 | 진단 설정(AuditEvent / Storage 로그 → 작업 영역) 확인 |
| 확인 불가 — 권한 없음 | 로그를 읽을 권한이 없음 | 범위에 Reader(리소스 로그 읽기 포함), 작업 영역 접근 모드 '리소스 또는 작업 영역 권한' |
| 확인 불가 — 기록하는 로그 없음 | 제어 평면 역할(Contributor 등 — 읽기는 Activity Log에 안 남음)·AcrPull·관리 그룹 범위 | 판정하지 않음 |

**지우기 전에**: 월말·분기 배치처럼 30일보다 드물게 쓰는 작업이 있는지, 로그 보존 기간이 30일보다 짧지 않은지, 같은 ID가 다른 범위의 역할로 같은 리소스를 쓰는지 확인하세요. 예: Key Vault CSI 드라이버를 워크로드 ID 모드로 쓰면 **추가 기능 ID의 Key Vault 역할은 쓰이지 않아** WI-18로 나옵니다 — 이 경우 지워도 됩니다.

### 5.3 SP(앱 등록) — '관리 ID · SP' 열과 WI-19

워크로드의 client-id가 연결된 구독의 관리 ID가 아니면, 대시보드는 그 클러스터 연결의 신원으로 **Microsoft Graph**에 물어 정체를 알아냅니다. 이 기능은 연결 파일의 `entra.readApplications: true`로 켜며, 그 연결의 앱에 `Application.Read.All` 애플리케이션 권한과 관리자 동의가 필요합니다. 끄면 이전처럼 '관리 ID로 찾지 못함 — SP 조회 꺼짐'으로 나옵니다.

| Graph 답 | 화면 | 읽는 것 |
|---|---|---|
| 앱 등록(Application) | **SP 카드**(같은 열, 'SP' 표시) | 이름, 로그인 허용 여부, Azure 역할(Resource Graph — 개체 ID로), API 권한(애플리케이션 권한 — 디렉터리 쓰기·모든 사서함 등은 '높은 권한'), 비밀·인증서 **개수와 만료일**, 앱의 페더레이션 자격 증명 |
| 다른 테넌트의 앱(멀티테넌트) | SP 카드 + '다른 테넌트의 앱' | 이름·역할·API 권한만(자격 증명은 그 테넌트에 있음) |
| 관리 ID(ManagedIdentity) | 관리 ID 카드 + '연결 밖 구독' | Graph가 알려 준 ARM ID로 역할·자격 증명 — 그 구독을 읽는 연결이 없으면 일부만 |
| 없음 | '이 테넌트에 이 client-id의 SP가 없음' | 삭제된 앱이거나 다른 테넌트의 client-id |

비밀 값·이름, 개체 ID, 전체 GUID는 화면과 응답에 넣지 않습니다(이름·끝 4자리·개수·날짜만).

**WI-19**(주의): 서비스 계정이 페더레이션 자격 증명으로 이 SP에 로그인하는데, 앱 등록에 비밀이나 인증서가 **아직 남아 있는** 경우입니다. 페더레이션이면 비밀이 필요 없고, 남은 비밀이 새어 나가면 클러스터 밖 어디서든 이 SP로 로그인할 수 있습니다(Learn: "These credentials pose a security risk and have to be stored securely and rotated regularly"). CI·스크립트가 그 비밀을 쓰지 않는지 확인한 뒤 지우세요. **만료된 것만** 남아 있으면 '참고'입니다(정리만 하면 됨).

Azure 역할도 API 권한도 없는 SP가 나오면 두 경우 중 하나입니다. 하나는 그 토큰을 자기 앱의 API(사용자 지정 audience)나 Key Vault 접근 정책·리소스 자체 권한(데이터베이스 사용자 등)에 쓰는 경우이고, 다른 하나는 쓰이지 않는 SP입니다. stg 실측(2026-11-06)에서 client-id 6종 중 5종은 관리 ID, 1종은 SP(역할 0·API 권한 0·FIC 1·비밀 1, 2027-06 만료)였습니다. stg의 Key Vault 12개는 모두 RBAC 방식이라 접근 정책은 없었습니다.

## 7. 그래프 탐색 (AKS 보안 점검 › 위험 개요 › 그래프 탐색)

"이런 워크로드가 있나?"를 직접 묻는 화면입니다. 조건을 고르면 **모두 만족하는 워크로드**를 찾습니다(그리고 = AND).

1. **자주 쓰는 질문**을 누르거나, 묶음(노출·이미지·실행·Kubernetes 권한·Azure ID·네트워크·**통신하는 Azure 리소스**·운영)에서 조건 칩을 고릅니다. 칩에 마우스를 올리면 그 조건이 무엇으로 판정되는지 보입니다
2. 결과: **일치 n**(모든 조건이 '예') · **판단 불가 m**(아니요는 없지만 데이터가 없는 조건이 있음 — 접힌 목록, 줄마다 이유) · 대상 워크로드 수
3. 워크로드를 누르면 상세 — 조건별 사실과 근거 칩, 닿을 수 있는 Azure ID(워크로드 ID / IMDS)와 역할, 통신한 Azure 리소스(외부 접근·키 인증·Defender 높음/중간/낮음과 권고 제목 3개), '히트맵에서 보기'·'공격 경로'
4. 질문 공유: 주소창의 `?tab=explore&q=…`를 그대로 보내면 같은 질문이 열립니다. '이 브라우저에 저장'은 이 PC의 이 브라우저에만 남습니다
5. **팀 질문**(운영자): 이름을 쓰고 '팀에 저장' — 같은 구독의 모든 사람에게 '팀' 칩으로 보입니다. **'이슈 목록에 감시'**를 켜고 등급을 고르면, 통합 위험 › 이슈 목록이 열릴 때마다 그 질문을 다시 풀어 **일치한 워크로드마다 이슈**를 올립니다(출처 '감시 질문'). 칩 옆 '감시 끄기'·×(삭제). 다른 사람이 먼저 바꿨으면 '다른 사람이 먼저 바꿨습니다' → 목록이 다시 읽힘

통신하는 Azure 리소스 조건은 **Hubble로 실제 통신이 관측된** 리소스만 봅니다(설정상 닿을 수 있는 리소스가 아님). Defender 권고는 그 리소스의 ID로 정확히 읽습니다 — 보안 개요의 권고 표본(5개)과 달리 빠짐이 없습니다.

## 8. 네트워크 정책 시뮬레이션 (AKS 보안 점검 › 네트워크 노출 › 정책 시뮬레이션)

> **5살 비유**: 놀이터 문 지키기 연습이에요. 어제 친구들이 실제로 드나든 길(Hubble이 본 연결)을 그대로 두고, "이 문을 잠그면?" "이 표지판을 떼면?" 하고 바꿔 보면 **누가 못 들어오게 되는지(새로 막힘)**, **누가 새로 들어올 수 있는지(새로 열림)** 바로 보여 줘요. 진짜 문은 건드리지 않아요.

1. **위 숫자**: 관측 연결 수 · 지금 정책으로 **● 규칙 허용 · ▲ 열림 · ■ 차단 · ? 판단 불가** · 바꾼 뒤 **새로 막힘**(지금 통과하는 연결 — 장애 위험) · **새로 열림** · **판정 ≠ 관측**(지금 정책 판정과 Hubble의 통과·드롭이 다름 — 정책이 바뀌었거나 모델이 모르는 규칙)
2. **연결 지도**(행 = 출발 네임스페이스, 열 = 도착 네임스페이스·API 서버·Azure 리소스·Azure 서비스·사설망·인터넷·노드): 칸 = 플랫폼 공통 상태 문법(라이브 카드·워크로드 히트맵과 같은 색·기호, 색만으로 구분하지 않음)

   | 기호 | 상태 | 뜻 |
   |---|---|---|
   | ● 초록 | 규칙이 허용 | 기본 거부 속에서 어떤 허용 규칙이 통과시킴 — 정책이 판단함 |
   | ▲ 주황 | 열림 — 검사 없음 | 양쪽 다 격리 안 됨, 아무 정책도 검사하지 않음(보안 공백) |
   | ◧ 빨강 | 일부 차단 | 포트 일부만 막힘 |
   | ■ 빨강 | 차단 | 막힘 |
   | ? 회색 점선 | 판단 불가 | 라벨·CIDR·이름 포트 등으로 확인 못 함 |

   칸 오른쪽 위 **파란 점** = 바꾼 뒤 달라짐(선택한 칸의 파란 테두리와 구분), **↓n** = 새로 막힘, **↑n** = 새로 열림, **!** = 판정 ≠ 관측
3. **칸을 누르면**(상세가 화면으로 스크롤됨)
   - **세 칸 요약** — ■ **막은 곳**(어느 정책이 격리했는데 허용 규칙이 없었는지 / deny 규칙) · ● **통과시킨 규칙(예외)**(정책 이름 + **규칙 번호와 내용**: `→ 같은 네임스페이스 파드 app=web · TCP 8080`) · ▲ **검사하지 않는 곳**(어느 네임스페이스의 어느 방향에 격리 정책이 없는지), 각각 연결 수
   - **연결마다 경로** — `출발 → [송신 검사] → [수신 검사] → 도착`. 검사마다 통과·막힘·검사 없음·항상 허용(노드)·해당 없음(인터넷·Azure 쪽은 파드가 아님)과 결정한 정책·규칙. 포트별 판정이 같으면 한 줄로 묶음
   - 바꾼 것이 있으면 '바꾼 뒤 / 지금'으로 기준을 바꿔 보고, 검사마다 '지금은 ● 통과'처럼 이전 판정이 함께 나옴
4. **바꿔 보기**(왼쪽): 네임스페이스를 고르고
   - 정책 체크 끄기 = 그 정책을 지우면?
   - 관찰용 정책의 **'강제로 바꾸면?'** — `enableDefaultDeny: false`(허용만 더하고 아무것도 막지 않음)를 강제로 바꿀 때 끊기는 연결. 위 안내의 **'모두 강제로 바꾸면?'**은 관찰용 전부
   - **+ 기본 거부(수신/송신)** — 그 네임스페이스 모든 파드에 default-deny
   - **+ DNS 허용** — kube-system의 kube-dns UDP/TCP 53
   - **허용 규칙을 빼면?** — 그 네임스페이스 정책을 모두 끄고 기본 거부(수신·송신)만 남김: 지금 허용 규칙이 **무엇을 통과시키고 있는지**가 '새로 막힘'으로 보임
   - **+ 관측된 수신/송신만 허용** — 지금 실제로 통과한 연결만 허용하는 초안(파드 = 라벨 + 네임스페이스, 외부 = 본 IP /32, 노드·API 서버 = 엔터티). 기본 거부 + 이것 = '새로 막힘 0'이면 그 초안으로 강제 전환을 시작할 수 있다는 뜻
   - 바꾼 것마다 칩 아래에 **그 변경 하나의 효과**(새로 막힘·새로 열림·상태 바뀜·격리 ±)가, 효과가 없으면 **이유**가 나옵니다

> **'기본 거부'를 넣었는데 아무것도 안 막혀요** — 정상입니다. 허용 규칙은 **합집합**이라, 다른 정책으로 이미 격리된 네임스페이스에 기본 거부를 더해도 기존 허용 규칙이 관측된 연결을 그대로 통과시킵니다(2026-11-02 stg 실측: integration·monitor·argocd 모두 이미 송신 격리 → 기본 거부 추가 = 새로 막힘 0, '허용 규칙을 빼면?' = 29·7·8). 기본 거부가 바꾸는 것은 **열림(격리 없음)** 연결뿐입니다.

5. **격리된 워크로드 표**: 네임스페이스마다 수신·송신 격리 워크로드 수, 지금 → 바꾼 뒤(초록 = 늘어남, 빨강 = 줄어듦 — 뚫림)

| 판정 규칙(Cilium — Kubernetes NetworkPolicy와 CiliumNetworkPolicy를 함께) | |
|---|---|
| 격리 | 그 방향을 기본 거부로 두는 정책이 하나라도 파드를 고르면 격리. **`enableDefaultDeny: false`는 격리가 아님**(허용만 더함) |
| 통과 | 격리 안 됨 = 모두 통과. 격리됨 = 고르는 정책의 허용 규칙 하나라도 상대·포트가 맞으면 통과 |
| deny | `ingressDeny`/`egressDeny`가 맞으면 다른 허용보다 먼저 차단 |
| 노드 | 노드(kubelet 프로브)에서 파드로 오는 연결은 항상 허용 |
| 연결 | 보내는 쪽 송신 + 받는 쪽 수신이 모두 통과해야 통과 |
| 판단 불가 | 관측 IP가 없는 CIDR 규칙 · 본 DNS 이름과 안 맞는 FQDN · 이름 붙은 포트 · 라벨을 모르는 파드 · 모델 밖 필드(toServices·toGroups·fromRequires·icmps) — '허용'도 '차단'도 아님 |

주의: 관측은 Hubble 버퍼 구간(바쁜 노드는 몇 분)뿐입니다. '새로 막힘 0'은 **본 연결**에 대한 말이고, 밤에만 도는 배치 같은 다른 시간대의 연결까지 안전하다는 뜻은 아닙니다. Cilium `policy-audit-mode`라면 deny 판정이어도 실제로는 드롭되지 않아 '판정 ≠ 관측'으로 보입니다.

**네트워크 정책 탭의 격리 수**도 같은 규칙으로 셉니다 — 관찰용 정책은 표에 **'관찰용 — 차단 안 함 (Egress)'** 배지가 붙고 격리 수에 들어가지 않습니다(2026-10-30 수정 전에는 들어갔음).

| 높음 | 10점 감점 | 하나라도 있으면 그 영역은 **최대 79점**(초록 80 이상이 되지 않음, 카드에 '높음 → 최대 79') |
| 점검 대상 없음 | 100점 | **'—'·'점검할 객체 없음'**(종합 평균에서 뺌) |
| 카드 보조 줄 | — | '문제 없음 n/m'(점검한 객체 m개 중 발견 없는 n개) |

**점검 대상(객체)** — 시스템 객체 제외: Pod Security·네트워크 정책 = 네임스페이스(+ 문제가 있는 정책), RBAC = 바인딩 + 워크로드(ServiceAccount 토큰), 오토스케일링·가용성 = Deployment·StatefulSet(+ 문제가 있는 HPA·VPA·PDB — 건강한 설정 객체는 워크로드 비율을 묽게 하므로 세지 않음), 리소스 = 워크로드 + 워크로드가 있는 네임스페이스.

**왜 바꿨나**: 예전 식은 클러스터 크기와 무관해, 위험 바인딩 9개면 다른 바인딩이 몇백 개여도 RBAC 0점, 규칙이 하나도 안 걸리는 영역은 무엇이 빠졌든 100점이었습니다. stg 실측(2026-11-03): **오토스케일링·가용성 100점 = 레플리카 1개를 보는 규칙이 없었음** — 사용자 워크로드 40개 중 15개가 레플리카 1개(argocd 8·monitoring 5 등), HPA 0개, 레플리카 2개 이상은 모두 PDB·분산 배치가 있었음.

**AVL-001 레플리카 1개** (중간): Deployment·StatefulSet의 최소 파드 수가 1(replicas 1, HPA가 있으면 `minReplicas` 1)이면 재시작·노드 업그레이드·드레인·OOM 동안 서비스가 멈춥니다. replicas 0(일부러 내림)은 제외. 조치 = 2개 이상 + PDB `maxUnavailable: 1` + `topologySpreadConstraints`(hostname). 여러 개로 늘릴 수 없는 단일 인스턴스(StatefulSet DB 등)는 이슈 목록에서 **예외**로 표시합니다(근거: [AKS 안정성 모범 사례](https://learn.microsoft.com/azure/aks/best-practices-app-cluster-reliability)).

## 10. AKS 관리 부품 (AKS 보안 점검 › 인벤토리 › AKS 관리 부품)

> **5살 비유**: 아파트 엘리베이터는 관리실이 고쳐요. 우리는 못 고치고, 게시판에서 "언제 고쳐요?"만 볼 수 있어요. 이 화면이 그 게시판이에요.

ama-logs·ama-metrics·Cilium·CNS·CSI·Defender·Azure Policy·CoreDNS처럼 **AKS가 설치·관리하는 이미지**(`mcr.microsoft.com`, kube-*·aks-*·azure-*·gatekeeper-system 등)는 고객이 패치할 수 없습니다. Microsoft 원칙([Learn](https://learn.microsoft.com/azure/aks/concepts-vulnerability-management)): 벤더 수정이 있는 CVE는 매주 다시 빌드하고, 최신 노드 이미지라면 벤더 수정이 나온 지 30일 넘은 컨테이너 이미지 CVE는 남지 않습니다.

| 판정 | 뜻 | 할 일 |
|---|---|---|
| ▲ Microsoft 수정 대기 | Microsoft가 내놓은 **가장 새 태그에도** 남아 있음(대부분 벤더 수정 대기) | 기다림 — KEV면 Azure 지원에 일정 문의 |
| ↑ 새 태그에서 고쳐짐 | 더 새 태그(스캔 있음)에는 없음 | 다음 AKS 릴리스·추가 기능 업데이트·클러스터 업그레이드로 받음 — 이 리전 도착은 위 '이 리전의 AKS 릴리스' |
| ? 판정 불가 | 비교할 더 새 태그의 스캔이 아직 없음 | — (깨끗하다는 뜻 아님) |
| ■ KEV | CISA가 실제 악용을 확인 | Microsoft·Azure 지원에 문의 |
| 보고서 없음 | 이 태그의 Microsoft 스캔이 없음(최근 스캔보다 새 빌드 — ama-*는 릴리스 사이에 자주 바뀜) | 다음 스캔 뒤 다시 |

**어떻게 판정하나**(`services/aksManagedVulns.ts`): 실행 중인 이미지(파드 `imageID`)마다 [AKS 취약점 데이터 API](https://learn.microsoft.com/azure/aks/security-vulnerability-api-reference)의 `container-images/<이미지>:<태그>/scan-reports`(Microsoft의 trivy 스캔) → 같은 이미지의 더 새 태그(최신 AKS 릴리스·이 리전 릴리스·클러스터 Kubernetes 버전 보고서에서, 새 것부터 스캔이 있는 것 최대 3개 시도)와 CVE 목록 비교. 이미지별 '조치 보고서'(mitigation-reports)는 이미지 하나가 최대 8MB라 쓰지 않습니다. 이 리전의 AKS 릴리스는 [AKS 릴리스 추적](https://releases.aks.azure.com)의 데이터(`parsed_data.json`, 약 25MB — 6시간에 한 번 읽고 작은 값만 보관). 노드 이미지는 노드 라벨 `kubernetes.azure.com/node-image-version` → `vhd-releases/<distro>/<버전>/scan-reports`(OS 패키지 — 커널은 버전만으로 대부분의 커널 CVE와 맞아 숫자가 큼, 한 줄로 묶음). 심각도 = CVE.org, 악용 = CISA KEV. 결과는 30분 캐시(일부 실패·CVE 상세 대기 중이면 2분).

stg 실측(2026-11-03, 리전 릴리스 v20260925 · 최신 v20261025 미도착): 관리 이미지 51개 중 Microsoft 스캔 있음 34개, 서로 다른 CVE 87개 — 새 태그에서 고쳐짐 62·수정 대기 113·판정 불가 40(이미지별 합계), KEV 1. CoreDNS v1.14.7-2의 CVE 28개 중 26개는 v1.14.7-6에서 고쳐짐, Cilium·CNS·Defender는 이미 가장 새 태그(남은 CVE 전부 Microsoft 수정 대기). 노드 이미지 Ubuntu 24.04 202610.23.0 = 이 리전 최신 빌드, CVE 3,254개 중 커널 3,183개.

네트워크: API가 `cve-api.prod-aks.azure.com`·`releases.aks.azure.com`에 GET(Microsoft 이미지 이름만 — 앱 이미지 이름은 보내지 않음). 쿠버네티스 차트는 `features.advisoryFeeds`가 켜져 있으면 두 FQDN을 허용, `AUD_ADVISORY_FEEDS=false`면 이 화면은 '꺼짐'.

## 보안 권고의 한국어 문구 (2026-11-11)

화면 언어가 한국어면 보안 권고의 제목 · 설명 · 조치 방법을 **Microsoft가 제공하는 공식 한국어 문구**로 보여 줍니다. 기계 번역이 아니고, 권고 내용이 외부 번역기로 나가지도 않습니다.

- 출처: Defender for Cloud의 평가 메타데이터 목록(`Microsoft.Security/assessmentMetadata`)을 `Accept-Language: ko-KR`로 읽어 권고의 평가 키로 맞춥니다(`apps/api/src/services/assessmentTexts.ts`). 하루 동안 캐시합니다.
- Microsoft가 한국어를 제공하지 않는 권고(사용자 지정 권고, 일부 새 권고)는 영어 그대로이고, 목록 아래에 'n개는 영어로 표시'라고 적습니다. 한국어 목록을 읽지 못하면 전체가 영어로 나오고 그 사실을 적습니다(1분 뒤 다시 시도).
- 조치 방법의 하위 단계(a. b.) 앞에 `&emsp;`가 글자 그대로 보이던 문제는 Defender HTML의 들여쓰기 기호를 풀지 않아 생긴 버그였고, 지금은 들여쓰기로 보입니다. 1,200자에서 잘리던 조치 방법도 끝까지 나옵니다.

## 11. 위협 탐지 문구의 한국어 (2026-11-12)

Azure는 Defender 경고의 제목·설명·조치 단계를 **영어로만** 줍니다(`Accept-Language: ko-KR`로 물어도 같은 영어 — 실측). 보안 권고는 Microsoft 공식 한국어가 있지만 경고는 없습니다.

| 순서 | 방법 | 화면 표시 |
|------|------|-----------|
| 1 | 대시보드가 가진 문장 표(문장 전체가 같을 때만) | '대시보드 번역' + 원문은 마우스를 올리면 |
| 2 | Azure Translator(`AZURE_TRANSLATOR_KEY`가 있을 때만) | '기계 번역' + 원문 |
| 3 | 그대로 영어 | 'Azure가 영어로만 제공' |

- 표에 있는 유형: kubelet kubeconfig 파일 액세스(`K8S.NODE_KubeConfigAccess`), 중요한 볼륨 탑재 컨테이너(`K8S_SensitiveMount`). 새 유형이 보이면 `services/alertTextsKo.ts`에 문장을 더합니다.
- 리소스 이름·네임스페이스·Pod 같은 대상 정보는 번역하지 않습니다.
- 검색은 화면에 보이는 문구(한국어)로 합니다.
