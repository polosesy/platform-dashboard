# 네트워크 경로 — 사용자 장치에서 SaaS까지, 홉별 지연·손실

메뉴 **네트워크 › 네트워크 경로**(`/network-path`)입니다. Datadog의 *End User Device Monitoring + Network Path*에 해당합니다. 사용자의 장치에서 SaaS(예: Microsoft 365 로그인)까지 네트워크 경로를 홉마다 재고, 지연·손실과 그 이력을 보여 줍니다.

> **5살 비유**: 집에서 학교까지 가는 길에 신호등이 몇 개 있고, 어느 신호등에서 오래 기다렸는지 적어 오는 숙제예요. 숙제는 아이(장치)가 직접 걸으면서 적고, 선생님(대시보드)은 그 공책을 받아서 어디가 막히는지 그림으로 보여 줘요. 신호등 하나가 "대답을 안 했다"고 해서 길이 막힌 건 아니에요 — 그 뒤 신호등들이 모두 대답하면 길은 잘 뚫려 있는 거예요.

## 1. 왜 장치에서 재나

| 위치 | 홉별 traceroute | 이유 |
|---|---|---|
| 브라우저 | 불가 | TTL을 정할 수도, ICMP를 받을 수도 없음(HTTP 타이밍만) |
| 대시보드 컨테이너 | 불가 · 의미 없음 | 셸·NET_RAW 없는 강화 이미지(65532), 그리고 경로의 시작이 사용자 장치가 아니라 클러스터 |
| **사용자 장치** | 가능 | Windows: .NET `Ping`에 TTL 지정(`IcmpSendEcho` — 관리자 불필요, 언어 설정과 무관) · macOS/Linux: `mtr` |

Datadog은 장치에 에이전트를 깝니다. 여기서는 **측정 스크립트**(`scripts/netpath-probe.ps1`, 화면에서 복사)를 장치에서 실행하고 결과(JSON)를 올립니다. 대시보드는 인터넷을 직접 재지 않습니다.

## 2. 측정 → 올리기 → 계산

1. **스크립트**(형식 `aud-netpath/1`): TTL 1부터 목적지가 답할 때까지, TTL마다 `-Probes`(기본 10)번 ICMP를 보냅니다. 기록하는 값은 **원시 사실만**입니다 — 응답한 주소별 횟수, 보낸·받은 수, 응답마다 왕복 시간(ms). .NET이 'TTL 만료' 응답의 왕복 시간을 0으로 주는 시스템에서는 그 탐침의 스톱워치 시간을 씁니다(약 1ms 이내 오버헤드). IPv4만.
2. **mtr**: `mtr --json -n -c 10 <대상>` 보고서를 그대로 받습니다. mtr JSON에는 요약값(Best·Avg·Wrst·Loss%)만 있어 그대로 씁니다. 호스트 `???` = 응답 없음.
3. **올리기**: 화면에 붙여 넣기 → `POST /api/netpath/runs`(로그인 사용자 — 자기 장치에서 잰 것). 서버가 형식을 검사하고(`parseNetPath`, zod, 256KB, 홉 64, 주소는 IPv4만) 홉마다 계산합니다.
   - 손실 = (보냄 − 받음) / 보냄
   - 지연 = 받은 탐침의 최소·평균·최대
   - 주소 = 가장 많이 답한 것(나머지는 '같은 홉의 다른 주소' — 부하 분산)
   - 범위 = 사설(RFC 1918) · CGNAT(100.64/10) · 공용
4. **저장**: `<AUD_ARRANGEMENT_DIR>/netpath/runs.json`(없으면 메모리 + 화면 경고), 최신 500개. 지우기는 운영자(`DELETE /api/netpath/runs?id=`).

**하지 않는 것**: 주소의 소유자(AS)·위치·역방향 DNS를 밖에 묻지 않습니다 — 사용자의 경로 주소를 외부 서비스로 보내지 않기 위해서입니다. 그래서 Datadog처럼 AS 단위로 묶지 않고 사설·CGNAT·공용만 표시합니다.

## 3. 읽는 법 (`lib/netPathView.ts`)

네트워크 엔지니어가 mtr·pathping 결과를 읽는 방식 그대로입니다.

| 판정 | 조건 | 화면 |
|---|---|---|
| 경로 손실 | 손실이 그 홉부터 **목적지까지 이어짐**(응답 없는 홉은 건너뜀) | ▲ 주황 테두리, 'n번 홉부터 손실' |
| ICMP 제한 | 중간 홉에만 손실, 뒤 홉·목적지는 정상 | ◌ 색 없음 — 라우터가 자기에게 오는 ICMP 응답을 줄인 것, 경로 손실 아님 |
| 응답 없는 홉 | 모든 탐침에 무응답(`*`) | ○ 점선, '숨기기' 토글(개수는 남김) |
| 목적지 응답 없음 | 목적지가 답하지 않음 | ■ 빨강 |
| 증가 | 그 홉의 평균 − 앞에서 응답한 홉의 평균(양수만) | '+n ms' — 지연이 늘어나는 곳 |

구간: 앞쪽 사설 홉 = '장치 주변 사설망' → 'ISP · 인터넷 구간' → '목적지'. 같은 SaaS 이름이라도 DNS가 측정마다 다른 IP를 줄 수 있어(Traffic Manager 등) **측정에 쓴 IP**를 함께 보이고, 이력에서 경로가 이전과 바뀌면 '이전과 바뀜'으로 표시합니다.

## 4. 검증 (2026-11-18)

| 대조 | 결과 | 기준 |
|---|---|---|
| 스크립트 실측(개발 PC → login.microsoftonline.com, 탐침 5) | 17홉, 목적지 도달, 11초 | — |
| 같은 IP로 Windows `tracert -d`(별도 도구) | 17홉 = 17홉, TTL별 같은 주소 14 · 둘 다 무응답 3 · 다름 0 | `tracert` 원문 |
| 이름으로 `tracert`(IP 다시 조회) | 15홉·다른 경로 — DNS가 다른 IP를 줌 | 측정 IP를 함께 기록·표시하게 한 근거 |
| 홉별 손실·평균 | 17/17 = 원시 JSON을 따로 계산한 값 | 독립 계산 |
| 화면(로컬 웹 + 헤드리스 Chrome, 실측 결과) | 홉 카드 17 · 정상 11 · ICMP 제한 3(10·12·13번 20% — 목적지 0%) · 무응답 3 · 가장 큰 증가 10번 홉 +60ms · 화면에서 올리기 → 이력 2 → 3 · 가로 넘침 0 | DOM 측정 |

mtr 형식은 공개 문서의 JSON 모양으로 단위 테스트만 했습니다(macOS·Linux 실측 없음). 테스트 `netPath.test.ts`(파서·판정·이력·저장·화면의 스크립트 = `scripts/netpath-probe.ps1`).

## 5. 남은 일

- **정기 측정**: 장치의 작업 스케줄러가 스크립트를 돌리고 바로 올리려면, 장치가 API 토큰을 얻는 길(디바이스 코드 로그인 등)이 필요합니다. 지금은 사람이 올립니다.
- **AS·위치**: 사내 승인된 IP 정보 출처가 생기면 홉을 AS로 묶을 수 있습니다.
- **IPv6**, TCP 기반 탐침(ICMP를 막는 망) — 스크립트가 아직 지원하지 않습니다.
